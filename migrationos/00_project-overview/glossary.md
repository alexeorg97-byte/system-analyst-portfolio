# Glossary — MigrationOS

## 1. Назначение документа

Глоссарий фиксирует основные термины проекта MigrationOS и выравнивает их понимание между бизнесом, аналитиком, дизайном, разработкой, QA и заинтересованными сторонами.

Документ нужен, чтобы:

- избежать разного понимания одних и тех же терминов;
- отделить бизнес-термины от системных сущностей;
- унифицировать названия ролей, модулей, статусов и интеграций;
- использовать единый язык в требованиях, API, ERD, BPMN и тест-кейсах.

## 2. Бизнес-термины

| Термин | Определение | Пример / комментарий |
|---|---|---|
| Мигрант | Иностранный работник, находящийся на сопровождении агентства или работодателя | Пользователь мобильного приложения |
| Работодатель | Компания-клиент агентства, у которой работают мигранты | Видит только своих мигрантов |
| Агентство | Компания, которая оказывает миграционное сопровождение и ведет операционные процессы | Использует административную панель |
| Менеджер агентства | Сотрудник агентства, который ведет мигрантов, документы, заявки, запросы и коммуникации | Основной пользователь админ-панели |
| Руководитель агентства | Пользователь, который контролирует риски, проекты, эффективность менеджеров и аналитику | Имеет расширенные права |
| Проект | Внутренняя группировка мигрантов внутри агентства | Например: склад, стройка, завод, объект |
| Миграционное сопровождение | Набор процессов по контролю документов, сроков, проверок и услуг для иностранных работников | Патент, регистрация, медосмотр, ДМС |
| Аутстаффинг | Модель, при которой сотрудники формально оформлены через агентство, но работают у клиента | Влияет на связи мигрант—работодатель—агентство |
| Услуга | Операция или пакет работ, который мигрант или работодатель может заказать у агентства | Продление патента, регистрация, уведомление МВД |
| Заявка | Заказ услуги в маркетплейсе или через кабинет пользователя | Имеет статусный жизненный цикл |
| Запрос | Обращение мигранта к работодателю или агентству | Например, запрос справки или документа |
| Документ | Миграционный или персональный документ мигранта | Паспорт, патент, регистрация, СНИЛС, ИНН |
| Срок действия документа | Дата, до которой документ считается актуальным | Используется для уведомлений и риск-статусов |
| Риск | Потенциальная проблема, связанная с документами, сроками, РКЛ или нарушениями | Может быть нормальный, предупреждающий или критичный |
| Риск-статус | Категория риска по мигранту или документу | В норме / Внимание / Критично |
| Риск-скор | Числовая оценка риска от 0 до 100 | Используется для приоритизации действий |
| Compliance | Соответствие юридическим, миграционным и внутренним требованиям | Влияет на аудит, доступы, хранение документов |
| ПДн | Персональные данные пользователя | Паспорт, телефон, адрес, документы |

## 3. Документы мигранта

| Термин | Определение | Комментарий |
|---|---|---|
| Паспорт | Основной документ, удостоверяющий личность мигранта | Может иметь срок действия |
| Патент | Документ, дающий право иностранному гражданину работать в РФ в установленном регионе | Критичен для контроля сроков |
| Регистрация | Документ о постановке на миграционный учет по месту пребывания | Требует контроля срока |
| СНИЛС | Страховой номер индивидуального лицевого счета | Обычно без срока действия |
| ИНН | Идентификационный номер налогоплательщика | Обычно без срока действия |
| Медкнижка | Документ о прохождении медицинских обследований | Может требовать регулярного обновления |
| ДМС | Полис добровольного медицинского страхования | Может иметь срок действия |
| Договор | Документ, регулирующий трудовые или сервисные отношения | Может быть PDF и требовать подписи |
| Скан документа | Файл-изображение или PDF, загруженный в систему | Хранится в S3-compatible хранилище |
| Шаблон документа | Форма документа, по которой система может генерировать PDF | Например, уведомление МВД |

## 4. Роли системы

| Роль | Описание | Канал доступа |
|---|---|---|
| migrant | Мигрант. Видит свой профиль, документы, запросы, заявки, чат и уведомления | Мобильное приложение |
| employer | Работодатель. Видит только своих мигрантов, заявки, запросы и платежи | Веб-кабинет |
| manager | Менеджер агентства. Обрабатывает мигрантов, документы, заявки, запросы, задачи и чаты | Админ-панель |
| supervisor | Руководитель агентства. Видит аналитику, риски, проекты и расширенные отчеты | Админ-панель |
| superadmin | Системный администратор. Управляет ролями, пользователями, справочниками и настройками | Админ-панель |

## 7. Статусы

### 7.1. Риск-статусы

| Статус | Значение | Когда используется |
|---|---|---|
| В норме | Нет критичных проблем | Документы актуальны, РКЛ без проблем |
| Внимание | Есть потенциальная проблема | Документ скоро истекает |
| Критично | Требуется срочное действие | Документ просрочен или мигрант найден в РКЛ |

### 7.2. Статусы документа

| Статус | Значение |
|---|---|
| missing | Документ отсутствует |
| uploaded | Документ загружен |
| under_review | Документ на проверке |
| valid | Документ актуален |
| expires_soon | Документ скоро истекает |
| expired | Документ просрочен |
| rejected | Документ отклонен |

### 7.3. Статусы запроса

| Статус | Значение |
|---|---|
| created | Запрос создан |
| sent_to_employer | Запрос отправлен работодателю |
| sent_to_agency | Запрос отправлен агентству |
| in_progress | Запрос в работе |
| waiting_for_documents | Требуются дополнительные документы |
| completed | Запрос выполнен |
| cancelled | Запрос отменен |

### 7.4. Статусы заявки

| Статус | Значение |
|---|---|
| new | Новая заявка |
| documents_check | Проверка документов |
| in_progress | В работе |
| ready | Результат готов |
| closed | Заявка закрыта |
| cancelled | Заявка отменена |

### 7.5. Статусы платежа

| Статус | Значение |
|---|---|
| created | Платеж создан |
| pending | Ожидает оплаты |
| paid | Оплачен |
| failed | Ошибка оплаты |
| expired | Срок оплаты истек |
| refunded | Возврат выполнен |

## 9. Технические термины

| Термин | Определение | Комментарий |
|---|---|---|
| REST API | Архитектурный стиль API на основе HTTP-методов | GET, POST, PATCH, DELETE |
| Webhook | Входящее событие от внешней системы | Например, payment webhook или РКЛ webhook |
| JSON | Формат обмена данными | Используется в API |
| JWT | Токен авторизации | Используется для авторизованных API-запросов |
| 2FA | Двухфакторная аутентификация | Требуется для админ-панели |
| RBAC | Role-Based Access Control | Модель доступа на основе ролей |
| Idempotency | Свойство повторного запроса не создавать дубль операции | Важно для webhook |
| Retry | Повторная попытка обработки события | Используется при ошибках интеграций |
| Fallback | Резервный сценарий при недоступности основного | Например, PDF вместо API |
| Presigned URL | Временная ссылка на файл в S3 | Ограничивает срок доступа |
| Audit log | Журнал действий пользователей | Кто, что и когда сделал |
| Integration log | Журнал обмена с внешними системами | Нужен для расследования ошибок |
| Soft delete | Логическое удаление записи без физического удаления | Важно для аудита |
| Pagination | Постраничная выдача списков | Нужна для больших таблиц |
| Filtering | Фильтрация данных | Например, по статусу, работодателю, проекту |
| Sorting | Сортировка данных | Например, по дате, риску, сроку |
| Validation | Проверка корректности данных | Формат телефона, ИНН, размер файла |
| Error model | Единая модель ошибок API | code, message, details, trace_id |
| NFR | Нефункциональные требования | Производительность, безопасность, доступность |
| SLA | Соглашение об уровне сервиса | Например, время реакции на P1/P2 ошибки |

## 11. Правила именования

Для консистентности в документации используются следующие правила:

- роли в системе пишутся в нижнем регистре на английском: `migrant`, `employer`, `manager`, `supervisor`, `superadmin`;
- системные сущности пишутся в PascalCase: `ServiceOrder`, `AuditLog`, `IntegrationLog`;
- статусы в API пишутся в snake_case: `in_progress`, `waiting_for_documents`, `expires_soon`;
- пользовательские статусы в интерфейсе пишутся на русском: `В норме`, `Внимание`, `Критично`;
- идентификаторы требований пишутся с префиксом: `BR-001`, `FR-001`, `NFR-001`;
- идентификаторы тест-кейсов пишутся с префиксом: `TC-001`;
- идентификаторы открытых вопросов пишутся с префиксом: `Q-001`.
