# Assumptions and Constraints — MigrationOS

## 1. Назначение документа

Документ фиксирует допущения, ограничения, зависимости и открытые вопросы по проекту MigrationOS.

Этот артефакт нужен, чтобы:

- явно отделить подтвержденные требования от предположений;
- зафиксировать ограничения, влияющие на архитектуру и реализацию;
- показать зависимости от внешних систем;
- снизить риск неверной интерпретации требований;
- подготовить вопросы для уточнения с бизнесом, разработкой, юридическим блоком и владельцами интеграций.

---

## 2. Допущения

Допущения — это предположения, на которых строится проектирование системы. Их необходимо подтвердить с заказчиком или техническими владельцами до реализации.

| ID | Допущение | Влияние, если допущение неверно | Требует подтверждения |
|---|---|---|---:|
| ASM-001 | У каждого мигранта есть уникальная карточка в системе | Возможны дубли и ошибки в документах, заявках и уведомлениях | Да |
| ASM-002 | Номер телефона может использоваться для первичной привязки мигранта к карточке | Если номер неактуален, мигрант может не привязаться к профилю | Да |
| ASM-003 | Работодатель всегда связан только со своими мигрантами | Нужно пересмотреть модель доступа и связи employer—migrant | Да |
| ASM-004 | Один мигрант может быть привязан к одному работодателю в конкретный момент времени | При множественной занятости потребуется M:N-связь и история привязок | Да |
| ASM-005 | Проект — внутренняя группировка агентства, не видимая мигрантам и работодателям | Если проект виден клиентам, потребуется отдельная логика доступа и UI | Да |
| ASM-006 | SHERPA RPA уже существует и не разрабатывается в рамках MigrationOS | При отсутствии готового робота scope и сроки увеличатся | Да |
| ASM-007 | SHERPA RPA может передавать результаты проверки через API/webhook | Если доступен только файл/ручная выгрузка, изменится интеграционный контур | Да |
| ASM-008 | Результаты РКЛ-проверки можно однозначно связать с мигрантом | Иначе потребуется ручное сопоставление и обработка конфликтов | Да |
| ASM-009 | Для оплаты услуг используется платежный шлюз / СБП с webhook | Без webhook нельзя надежно подтверждать оплату на backend | Да |
| ASM-010 | Документы хранятся во внешнем объектном хранилище S3-compatible | При хранении в БД изменится архитектура файлового контура | Да |
| ASM-011 | Push-уведомления мигрантам отправляются через FCM | Для iOS/Android могут потребоваться дополнительные настройки и fallback | Да |
| ASM-012 | Мобильное приложение мигранта поддерживает RU / UZ / EN | Потребуются словари локализации и правила для всех пользовательских текстов | Да |
| ASM-013 | Админ-панель доступна только сотрудникам агентства | При доступе внешних ролей потребуется расширенная модель прав | Да |
| ASM-014 | 1С остается учетной системой, а MigrationOS не заменяет бухгалтерский и кадровый учет | При замене 1С scope существенно расширится | Да |
| ASM-015 | Все критичные действия пользователей должны логироваться | При отсутствии audit log возрастает риск споров и нарушений доступа | Да |

## 3. Бизнес-ограничения

| ID | Ограничение | Описание | Влияние на систему |
|---|---|---|---|
| BC-001 | Миграционное сопровождение связано с юридическими рисками | Ошибки в документах, сроках и проверках могут привести к штрафам | Нужны риск-статусы, уведомления, audit log и контроль сроков |
| BC-002 | Работодатель должен видеть только своих мигрантов | Данные других работодателей недоступны | Требуется строгая backend-авторизация |
| BC-003 | Агентство должно видеть всех мигрантов | Агентство отвечает за операционный контроль | Требуется отдельная роль с расширенным доступом |
| BC-004 | Часть процессов остается ручной | Не все услуги можно полностью автоматизировать | Нужны статусы, задачи менеджеров и комментарии |
| BC-005 | РКЛ-робот не входит в scope разработки | MigrationOS только принимает результаты | Нужен интеграционный контракт и fallback при недоступности |
| BC-006 | White Label исключен из текущей версии | Система не проектируется как мультиагентская SaaS-платформа | Не требуется tenant model для сторонних агентств |
| BC-007 | Мобильное приложение менеджера не входит в текущую версию | Менеджеры работают через web admin panel | Все рабочие сценарии менеджера должны быть доступны в админке |
| BC-008 | Интерфейс мигранта должен быть максимально простым | Пользователи могут иметь разный уровень цифровой грамотности и владения русским языком | Нужны простые сценарии, локализация, подсказки и минимизация полей |

## 4. Технические ограничения

| ID | Ограничение | Описание | Влияние на проектирование |
|---|---|---|---|
| TC-001 | Backend должен проверять права доступа | Нельзя полагаться только на скрытие элементов на frontend | Нужны authorization checks на API |
| TC-002 | Статус оплаты подтверждается только backend webhook | Frontend-событие не является надежным подтверждением оплаты | Нужна модель платежных статусов и идемпотентность webhook |
| TC-003 | Push-уведомления не гарантируют доставку | Пользователь может отключить уведомления или устройство может быть недоступно | Критичные события сохраняются как in-app уведомления |
| TC-004 | Внешние интеграции могут быть недоступны | РКЛ, 1С, платежный шлюз, email или FCM могут возвращать ошибки | Нужны retry, fallback, integration logs и алерты |
| TC-005 | Файлы документов требуют защищенного хранения | Документы содержат персональные данные | Нужны S3, контроль доступа, presigned URL, ограничения срока ссылки |
| TC-006 | Система должна поддерживать audit log | Важно фиксировать действия с документами, ролями, заявками и платежами | Нужны события аудита и неизменяемая история |
| TC-007 | Мультиязычность должна учитываться на уровне данных и UI | Тексты не должны быть захардкожены | Нужны ключи локализации и шаблоны уведомлений на RU / UZ / EN |
| TC-008 | Требуется обработка дублей webhook | Платежный шлюз или РКЛ-робот могут отправить повторное событие | Нужна идемпотентность по event_id / external_id |
| TC-009 | Списки могут быть большими | Потенциально тысячи мигрантов, документов, заявок и событий | Нужны пагинация, фильтры, индексы и сортировка |
| TC-010 | Логи интеграций не должны раскрывать чувствительные данные | В логах могут оказаться ПДн или реквизиты | Нужна маскировка чувствительных полей |

## 5. Ограничения безопасности и доступа

| ID | Ограничение | Описание | Требование |
|---|---|---|---|
| SEC-001 | Персональные данные мигрантов чувствительны | Паспорт, патент, регистрация, адрес, телефон, документы | Ограничение доступа по ролям |
| SEC-002 | Работодатель не должен получить доступ к чужим мигрантам | Основной риск B2B-кабинета | Backend authorization + проверка employer_id |
| SEC-003 | Ссылки на документы не должны быть постоянными | Постоянные ссылки повышают риск утечки | Presigned URL с ограниченным сроком действия |
| SEC-004 | Действия с документами должны логироваться | Важно видеть, кто открыл, изменил или загрузил документ | Audit log |
| SEC-005 | Админ-панель требует усиленной защиты | Доступ к полной базе и документам | 2FA для сотрудников агентства |
| SEC-006 | Удаление данных должно быть контролируемым | Нельзя бесследно удалять критичные данные | Soft delete / archive + audit trail |
| SEC-007 | Ошибки API не должны раскрывать лишние данные | Сообщения об ошибках могут раскрыть структуру системы | Единая error model без чувствительных данных |

## 6. Ограничения по данным

| ID | Ограничение | Описание | Влияние |
|---|---|---|---|
| DATA-001 | У мигранта может быть несколько документов одного типа в истории | Старые документы должны сохраняться для аудита | Нужна история версий или status/archive |
| DATA-002 | Документ имеет срок действия не всегда | Например, СНИЛС/ИНН могут не иметь срока | Поля expiry_date должны быть nullable |
| DATA-003 | Результат РКЛ-проверки должен иметь дату и источник | Риск-статус зависит от актуальности данных | Нужны поля checked_at, source, external_check_id |
| DATA-004 | Статусы должны быть нормализованы | Нельзя хранить произвольный текст статуса | Нужны справочники или enum |
| DATA-005 | Заявки и запросы похожи, но имеют разный бизнес-смысл | Запрос документа и заказ услуги не одно и то же | Нужны отдельные сущности или типизация |
| DATA-006 | Платеж должен быть связан с заявкой или счетом | Иначе сложно отследить оплату | Нужны связи payment—order/invoice |
| DATA-007 | Интеграционные события должны сохраняться | Нужно расследовать ошибки интеграций | Нужен integration_log |
| DATA-008 | Пользовательские действия должны сохраняться | Нужно расследовать спорные ситуации | Нужен audit_log |

## 7. Зависимости от внешних систем

| Система | Зависимость | Риск | Митигирующее решение |
|---|---|---|---|
| SHERPA RPA / РКЛ-робот | Получение результатов проверки РКЛ | Задержка или отсутствие данных | Алерт, отметка времени последней проверки, ручной fallback |
| 1С | Синхронизация учетных данных | Конфликт данных или задержка синхронизации | Очередь изменений, reconciliation report, integration log |
| Платежный шлюз / СБП | Подтверждение оплаты | Webhook не пришел или пришел повторно | Retry, idempotency key, ручная сверка |
| FCM | Доставка push | Уведомление не доставлено | In-app уведомления и история событий |
| S3-хранилище | Доступ к документам | Ошибка загрузки или скачивания | Повтор загрузки, временное хранение, сообщение пользователю |
| Email-сервис | Отправка писем и счетов | Письмо не доставлено | Retry, delivery status, возможность повторной отправки |
| Госуслуги / API МВД | Потенциальная интеграция | API может быть недоступен или ограничен | PDF/fallback-процесс через менеджера |

## 9. Риски проекта

| Риск | Вероятность | Влияние | Митигирующее действие |
|---|---:|---:|---|
| Недооценка сложности ролевой модели | Средняя | Высокое | Сначала согласовать role model и access matrix |
| Неполные требования к маркетплейсу | Высокая | Среднее | Вынести маркетплейс в отдельную детализацию |
| Неполный контракт РКЛ-интеграции | Средняя | Высокое | Подготовить OpenAPI / webhook contract до разработки |
| Ошибки доступа к документам | Средняя | Высокое | Backend authorization, тесты на 403, audit log |
| Некорректная обработка платежей | Средняя | Высокое | Webhook, идемпотентность, payment status model |
| Перегрузка мобильного интерфейса мигранта | Средняя | Среднее | Пошаговые сценарии, UX-тестирование, локализация |
| Задержка интеграции с 1С | Средняя | Среднее | Согласовать минимальный контракт и fallback-импорт |
| Непроработанные edge cases | Средняя | Среднее | Отдельный документ edge cases и тест-кейсы |
| Рост scope в процессе проекта | Высокая | Высокое | Поддерживать in scope / out of scope и change request процесс |

## 10. Выводы для проектирования

Ключевые выводы:

- ролевую модель и матрицу доступа нужно согласовать до проектирования API и UI;
- интеграционные контракты критичны для РКЛ, 1С и платежей;
- платежные и РКЛ-webhook должны быть идемпотентными;
- документы должны храниться защищенно, а доступ к ним должен проверяться на backend;
- критичные события нельзя завязывать только на push-уведомления;
- все важные действия должны попадать в audit log;
- статусы документов, заявок, запросов и платежей должны быть нормализованы;
- MVP должен закрывать основной end-to-end процесс без попытки автоматизировать все услуги сразу.
