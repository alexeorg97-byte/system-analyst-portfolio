# Non-Functional Requirements — MigrationOS

## 1. Назначение документа

Документ описывает нефункциональные требования к платформе MigrationOS.

Нефункциональные требования определяют, **как** система должна работать: насколько быстро, безопасно, надежно, масштабируемо и удобно.

Документ используется для:

- проектирования архитектуры;
- оценки технических ограничений;
- подготовки критериев приемки;
- подготовки нагрузочного, интеграционного и security-тестирования;
- согласования ожиданий между бизнесом, аналитиком, разработкой, QA и DevOps.

---

## 2. Категории NFR

Нефункциональные требования сгруппированы по категориям:

1. Производительность.
2. Масштабируемость.
3. Доступность и надежность.
4. Безопасность и доступ.
5. Персональные данные и документы.
6. Аудит и логирование.
7. Интеграции и webhook.
8. Платежи.
9. Уведомления.
10. Локализация.
11. Usability.
12. Совместимость.
13. Мониторинг и алерты.
14. Backup и восстановление.
15. Ограничения эксплуатации.

## 3. Производительность

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-001 | API должен отвечать за приемлемое время для основных пользовательских сценариев | p95 времени ответа для основных GET/POST/PATCH API ≤ 500 мс при нормальной нагрузке | Must |
| NFR-002 | Страницы веб-кабинетов должны загружаться без заметной задержки | Основной контент страницы отображается ≤ 2 сек при стабильной сети | Should |
| NFR-003 | Список мигрантов должен поддерживать работу с большими объемами данных | Таблицы используют пагинацию, фильтры и сортировку на backend | Must |
| NFR-004 | Загрузка документа не должна блокировать интерфейс пользователя | Пользователь видит прогресс или состояние загрузки | Should |
| NFR-005 | Обновление статуса заявки, запроса или платежа должно отображаться пользователю после следующего обновления данных | Статус доступен через API после успешной обработки события | Must |
| NFR-006 | Массовые списки не должны загружаться одним запросом без ограничений | Для списков используется limit/offset или cursor pagination | Must |

## 4. Масштабируемость

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-007 | Система должна поддерживать рост базы мигрантов без деградации ключевых сценариев | Поддержка не менее 10 000 мигрантов в БД | Must |
| NFR-008 | Система должна поддерживать рост количества работодателей | Архитектура данных не должна ограничивать количество работодателей фиксированным числом | Must |
| NFR-009 | Система должна поддерживать рост количества документов | Документы хранятся в объектном хранилище, а не как бинарные данные в основной БД | Must |
| NFR-010 | Очереди уведомлений и интеграционных событий должны масштабироваться отдельно от пользовательских API | Интеграционные и notification-сценарии не блокируют основные действия пользователя | Should |
| NFR-011 | Фильтрация по работодателю, проекту, статусу и риску должна быть рассчитана на большие списки | Для ключевых фильтров предусмотрены индексы в БД | Should |

## 5. Доступность и надежность

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-012 | Система должна быть доступна пользователям в рабочее время агентства и работодателей | Целевой uptime ≥ 99,5% в месяц | Should |
| NFR-013 | Недоступность внешней интеграции не должна полностью останавливать работу системы | При ошибке интеграции создается запись в integration log и пользователю показывается понятное состояние | Must |
| NFR-014 | Критичные операции должны иметь контролируемый результат | Пользователь не должен видеть “успех”, если операция на backend не завершена | Must |
| NFR-015 | Повторная отправка webhook не должна создавать дубли | Используется идемпотентность по external_event_id / idempotency_key | Must |
| NFR-016 | При ошибке загрузки документа пользователь должен иметь возможность повторить действие | Ошибка отображается явно, данные формы не теряются при возможности | Should |
| NFR-017 | Система должна обрабатывать истечение сессии пользователя | При истечении токена пользователь получает понятное состояние и переходит к повторному входу | Must |

## 6. Безопасность и доступ

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-018 | Все защищенные API должны требовать авторизацию | Запрос без токена возвращает 401 Unauthorized | Must |
| NFR-019 | Доступ к данным должен проверяться на backend | Пользователь не может получить чужие данные прямым API-запросом | Must |
| NFR-020 | Работодатель не должен получать доступ к мигрантам другой организации | Попытка доступа возвращает 403 Forbidden | Must |
| NFR-021 | Мигрант должен получать доступ только к своим данным | Попытка доступа к чужому профилю, документам или заявкам возвращает 403 Forbidden | Must |
| NFR-022 | Админ-панель должна поддерживать 2FA | Для ролей manager / supervisor / superadmin включается второй фактор | Must |
| NFR-023 | Пароли должны храниться в хэшированном виде | Пароли не хранятся в открытом виде | Must |
| NFR-024 | Ошибки API не должны раскрывать чувствительные данные | Ответ ошибки не содержит ПДн, токены, внутренние stack traces | Must |
| NFR-025 | Доступ к административным функциям должен быть ограничен ролями | Только разрешенные роли могут управлять пользователями, справочниками и настройками | Must |
| NFR-026 | Система должна учитывать базовые требования OWASP Top 10 | Проверка проводится на уровне security checklist | Should |

## 7. Персональные данные и документы

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-027 | Документы мигрантов должны храниться в защищенном хранилище | Файлы не доступны по постоянным публичным ссылкам | Must |
| NFR-028 | Доступ к файлам документов должен выдаваться через временные ссылки или защищенный backend-контур | Ссылка имеет ограниченный срок действия | Must |
| NFR-029 | Система должна хранить согласие на обработку персональных данных, если оно требуется процессом | Согласие связано с пользователем и имеет дату подтверждения | Must |
| NFR-030 | Критичные действия с персональными данными должны логироваться | Просмотр, изменение, загрузка и удаление фиксируются в audit log | Must |
| NFR-031 | Удаление документов должно быть контролируемым | Используется soft delete / archive или другое согласованное правило хранения | Should |
| NFR-032 | Система не должна выводить лишние персональные данные в списках | В таблицах отображается только необходимый минимум данных | Should |
| NFR-033 | Integration logs не должны хранить чувствительные данные в открытом виде | ПДн и реквизиты маскируются или не сохраняются в логах | Must |

## 8. Аудит и логирование

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|

| NFR-037 | Логи должны позволять расследовать спорные ситуации | По сущности можно восстановить историю ключевых действий | Must |
| NFR-038 | Логи не должны раскрывать секреты и токены | API keys, tokens, passwords не сохраняются в открытом виде | Must |

## 9. Интеграции и webhook

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-040 | Входящие webhook должны проверять источник события | Используется API key, signature, IP whitelist или другой согласованный механизм | Must |
| NFR-041 | Webhook должны обрабатываться идемпотентно | Повторное событие не создает дубль платежа, РКЛ-проверки или заявки | Must |
| NFR-042 | При ошибке обработки webhook событие должно сохраняться в integration log | Ошибка доступна для анализа и повторной обработки | Must |
| NFR-043 | Для интеграций должен быть предусмотрен retry-механизм, где это применимо | Временные ошибки повторяются по согласованному правилу | Should |
| NFR-044 | Внешняя система не должна блокировать основной пользовательский сценарий дольше допустимого времени | Долгие операции выполняются асинхронно | Should |
| NFR-045 | Интеграция с РКЛ должна сохранять дату и источник проверки | Карточка мигранта показывает актуальность РКЛ-данных | Must |
| NFR-046 | Интеграционные ошибки должны иметь понятную классификацию | Например: validation_error, auth_error, timeout, duplicate_event, external_unavailable | Should |

|---|---|---|---|
| NFR-047 | Статус оплаты должен подтверждаться только backend-событием от платежного провайдера | Frontend redirect не переводит платеж в `paid` без webhook | Must |

| NFR-051 | История платежей должна быть доступна пользователям с правами | Работодатель видит платежи своей организации, агентство — по своим правам | Should |
| NFR-052 | Финансовые события должны попадать в audit / integration log | Создание, изменение статуса и ошибки фиксируются | Must |

## 17. Ограничения эксплуатации

| ID | Требование | Метрика / критерий приемки | Приоритет |
|---|---|---|---|
| NFR-086 | Система должна иметь отдельные среды разработки, тестирования и production | dev / stage / prod | Should |
| NFR-087 | Изменения должны проходить проверку до production | Минимум: code review + QA на stage | Should |

## 18. Приоритизация

Для NFR используется MoSCoW:

| Приоритет | Значение |
|---|---|
| Must | Критично для безопасности, данных, MVP или ключевого бизнес-процесса |
| Should | Важно для качества продукта и эксплуатации, но может быть уточнено после MVP |
| Could | Желательно, но не критично для первой версии |
| Won't | Не входит в текущую версию |

---

## 19. Проверяемость NFR

NFR считается корректным, если его можно проверить одним из способов:

- функциональным тестированием;
- API-тестом;
- security checklist;
- нагрузочным тестированием;
- проверкой логов;
- проверкой прав доступа;
- просмотром UI-состояний;
- проверкой конфигурации;
- ревью архитектуры;
- тестированием интеграционного сценария.

---

## 20. Ограничения документа

- Документ не заменяет архитектурное описание.
- Детали реализации фиксируются в API, ERD, deployment context и технических задачах.
- Метрики могут быть уточнены после согласования целевой нагрузки и инфраструктуры.
- Часть требований зависит от выбранных внешних сервисов: платежного шлюза, email-провайдера, S3-хранилища и push-инфраструктуры.
