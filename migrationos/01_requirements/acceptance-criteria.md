# Acceptance Criteria — MigrationOS

## 1. Назначение документа

Документ описывает критерии приемки для ключевых сценариев платформы MigrationOS.

Acceptance Criteria нужны, чтобы:

- определить, когда требование считается выполненным;
- связать user stories с проверяемым поведением системы;
- подготовить основу для тест-кейсов;
- снизить неоднозначность между аналитиком, разработкой, QA и бизнесом;
- проверить ключевые сценарии MVP.

Критерии оформлены в формате:

```gherkin
Given [исходное состояние]
When [действие пользователя или событие]
Then [ожидаемый результат]
```

## 2. Принципы написания Acceptance Criteria

- Критерий должен быть проверяемым.
- Критерий должен описывать наблюдаемое поведение системы.
- Критерий не должен описывать внутреннюю реализацию без необходимости.
- Если сценарий зависит от роли, роль должна быть указана в `Given`.
- Если сценарий зависит от внешнего события, событие должно быть указано в `When`.
- Если сценарий связан с безопасностью, ожидаемый результат должен явно запрещать раскрытие данных.
- Если сценарий связан с интеграцией, критерий должен учитывать успешную обработку, ошибку и повторное событие.
- Если сценарий связан со статусами, критерий должен проверять допустимость перехода и сохранение истории.

## 3. Авторизация мигранта по OTP

**Связанные User Stories:** `US-MIG-001`  
**Связанные FR:** `FR-001`, `FR-002`, `FR-003`, `FR-004`

### AC-AUTH-001 — Успешный запрос OTP

```gherkin
Given пользователь находится на экране входа в мобильное приложение
And пользователь вводит корректный номер телефона
When пользователь нажимает "Получить код"
Then система отправляет OTP-код на указанный номер
And показывает экран ввода OTP-кода
```

### AC-AUTH-002 — Успешный вход по OTP

```gherkin
Given пользователь получил OTP-код
And пользователь находится на экране ввода OTP
When пользователь вводит корректный OTP-код
Then система авторизует пользователя
And выдает access token
And открывает главный экран мобильного приложения
```

### AC-AUTH-003 — Карточка мигранта не найдена

```gherkin
Given пользователь ввел корректный OTP-код
And в системе нет карточки мигранта, связанной с этим номером телефона
When система выполняет поиск карточки
Then система не открывает личный кабинет
And показывает сообщение о необходимости обратиться в агентство
```

### AC-AUTH-004 — Некорректный OTP

```gherkin
Given пользователь находится на экране ввода OTP
When пользователь вводит некорректный OTP-код
Then система не авторизует пользователя
And показывает ошибку "Неверный код"
And позволяет повторить ввод
```

## 4. Просмотр документов мигранта

**Связанные User Stories:** `US-MIG-004`, `US-MIG-005`  
**Связанные FR:** `FR-020`, `FR-021`, `FR-022`, `FR-031`, `FR-032`

### AC-DOC-001 — Просмотр списка документов

```gherkin
Given мигрант авторизован в мобильном приложении
When мигрант открывает раздел "Документы"
Then система показывает список документов мигранта
And для каждого документа отображает тип, статус и срок действия, если срок применим
```

### AC-DOC-002 — Документ без срока действия

```gherkin
Given у документа нет срока действия
When мигрант открывает список документов
Then система отображает документ без даты окончания
And не помечает документ как просроченный из-за отсутствия даты
```

### AC-DOC-003 — Документ скоро истекает

```gherkin
Given у документа есть срок действия
And срок действия попадает в период предупреждения
When система рассчитывает статус документа
Then документ получает статус `expires_soon`
And риск отображается как "Внимание"
```

### AC-DOC-004 — Документ просрочен

```gherkin
Given у документа есть срок действия
And срок действия меньше текущей даты
When система рассчитывает статус документа
Then документ получает статус `expired`
And риск отображается как "Критично"
```

## 5. Загрузка документа мигрантом

**Связанные User Stories:** `US-MIG-006`, `US-MIG-007`  
**Связанные FR:** `FR-023`, `FR-024`, `FR-025`, `FR-026`, `FR-027`, `FR-029`, `FR-030`

### AC-UPLOAD-001 — Успешная загрузка документа

```gherkin
Given мигрант авторизован
And мигрант находится в разделе документа
When мигрант выбирает файл допустимого формата и размера
And нажимает "Загрузить"
Then система загружает файл в защищенное хранилище
And создает или обновляет запись документа
And присваивает документу статус `under_review`
And показывает пользователю успешный результат загрузки
```

### AC-UPLOAD-002 — Недопустимый формат файла

```gherkin
Given мигрант выбрал файл недопустимого формата
When мигрант пытается загрузить файл
Then система не загружает файл
And показывает сообщение о допустимых форматах
```

### AC-UPLOAD-003 — Превышен размер файла

```gherkin
Given мигрант выбрал файл больше допустимого размера
When мигрант пытается загрузить файл
Then система не загружает файл
And показывает сообщение о максимальном размере файла
```

### AC-UPLOAD-004 — Отклонение документа менеджером

```gherkin
Given документ находится в статусе `under_review`
And менеджер открыл документ в админ-панели
When менеджер отклоняет документ и указывает причину
Then система переводит документ в статус `rejected`
And сохраняет причину отклонения
And фиксирует событие в истории документа
```

## 6. Создание запроса мигрантом

**Связанные User Stories:** `US-MIG-009`, `US-MIG-011`, `US-MIG-012`  
**Связанные FR:** `FR-036`, `FR-038`, `FR-039`, `FR-040`, `FR-042`, `FR-043`, `FR-044`, `FR-046`

### AC-REQ-001 — Запрос документа от работодателя

```gherkin
Given мигрант авторизован
When мигрант создает запрос документа от работодателя
Then система создает запрос со статусом `created`
And связывает запрос с мигрантом
And делает запрос доступным работодателю мигранта
And отображает запрос в админ-панели агентства
```

### AC-REQ-002 — Просмотр статуса запроса мигрантом

```gherkin
Given у мигранта есть созданный запрос
When мигрант открывает раздел "Запросы"
Then система показывает запрос
And отображает текущий статус запроса
And отображает дату создания запроса
```

### AC-REQ-003 — Смена статуса запроса

```gherkin
Given запрос существует в системе
And пользователь с правами открыл запрос
When пользователь меняет статус запроса
Then система сохраняет новый статус
And добавляет событие в историю запроса
And создает уведомление мигранту
```

### AC-REQ-004 — Недопустимый статусный переход запроса

```gherkin
Given запрос существует в системе
And пользователь с правами открыл запрос
When пользователь пытается установить недопустимый следующий статус
Then система не меняет статус запроса
And показывает сообщение о недопустимом переходе
And не создает ложное уведомление о смене статуса
```

## 7. Личный кабинет работодателя

**Связанные User Stories:** `US-EMP-001`, `US-EMP-003`, `US-EMP-004`, `US-EMP-005`, `US-EMP-006`  
**Связанные FR:** `FR-047`, `FR-049`, `FR-051`, `FR-052`, `FR-054`, `FR-055`, `FR-056`, `FR-124`

### AC-EMP-001 — Регистрация работодателя

```gherkin
Given пользователь находится на странице регистрации работодателя
When пользователь вводит обязательные данные организации
And отправляет форму регистрации
Then система создает работодателя в статусе `pending_verification`
And показывает сообщение, что кабинет будет доступен после проверки агентством
```

### AC-EMP-002 — Работодатель видит только своих мигрантов

```gherkin
Given работодатель авторизован
When работодатель открывает список мигрантов
Then система показывает только мигрантов, связанных с его организацией
And не показывает мигрантов других работодателей
```

### AC-EMP-003 — Запрет доступа к чужому мигранту

```gherkin
Given работодатель авторизован
And мигрант принадлежит другой организации
When работодатель пытается открыть карточку этого мигранта прямым API-запросом
Then система возвращает ошибку 403 Forbidden
And не возвращает данные мигранта
```

### AC-EMP-004 — Просмотр риск-дашборда

```gherkin
Given работодатель авторизован
When работодатель открывает дашборд
Then система показывает количество мигрантов по риск-статусам
And учитывает только мигрантов этой организации
```

### AC-EMP-005 — Работодатель не может редактировать карточку мигранта без прав

```gherkin
Given работодатель авторизован
And работодатель открыл карточку своего мигранта
When работодатель пытается изменить поля карточки, которые доступны только агентству
Then система запрещает изменение
And не сохраняет новые значения
And показывает ошибку доступа или недоступность действия
```

### AC-ADMIN-005 — Дашборд критичных рисков руководителя

```gherkin
Given руководитель агентства авторизован
```

## 10. Платежи и счета

**Связанные User Stories:** `US-EMP-010`, `US-EMP-011`, `US-FIN-001`, `US-FIN-002`  
**Связанные FR:** `FR-089`, `FR-090`, `FR-091`, `FR-092`, `FR-093`, `FR-096`, `FR-097`

### AC-PAY-001 — Создание платежа

```gherkin
Given заявка на платную услугу создана
When система инициирует оплату
Then система создает платеж в статусе `created` или `pending`
And связывает платеж с заявкой
```

### AC-PAY-002 — Frontend redirect не подтверждает оплату

```gherkin
Given платеж находится в статусе `pending`
And пользователь вернулся со страницы платежного провайдера
When payment webhook еще не поступил на backend
Then система не переводит платеж в статус `paid`
And отображает платеж как ожидающий подтверждения
```

### AC-PAY-003 — Подтверждение оплаты через webhook

```gherkin
Given платеж находится в статусе `pending`
When система получает валидный payment webhook со статусом успешной оплаты
Then система переводит платеж в статус `paid`
And сохраняет событие в integration log
And обновляет связанную заявку, если это предусмотрено бизнес-правилом
```

### AC-PAY-004 — Повторный payment webhook

```gherkin
Given payment webhook с указанным event_id уже был обработан
When система получает такой же webhook повторно
Then система не создает дубль платежа
And не выполняет повторное изменение статуса
And возвращает успешный технический ответ или согласованный duplicate response
```

### AC-PAY-005 — Формирование счета

```gherkin
Given пользователь с правами открыл заявку или заказ
When пользователь выбирает действие "Сформировать счет"
Then система создает PDF-счет
And связывает счет с заявкой или работодателем
And позволяет скачать или отправить счет на email
```

### AC-RKL-001 — Прием валидного РКЛ-события

```gherkin
Given SHERPA RPA отправляет валидное РКЛ-событие
When MigrationOS принимает событие
Then система валидирует payload
And сохраняет результат РКЛ-проверки
And связывает результат с карточкой мигранта
And сохраняет событие в integration log
```

### AC-RKL-002 — Мигрант найден в РКЛ

```gherkin
Given система получила РКЛ-событие
```

```gherkin

When система получает такое же событие повторно
Then система не создает дубль РКЛ-проверки
And не создает повторный алерт
And фиксирует повторное событие согласно правилам integration log
```

### AC-RKL-004 — Невалидное РКЛ-событие

```gherkin
Given SHERPA RPA отправляет РКЛ-событие с некорректным payload
When система валидирует событие
Then система не обновляет риск-статус мигранта
And сохраняет ошибку в integration log
And возвращает согласованный код ошибки
```

```gherkin
When superadmin открывает управление ролями
Then система показывает доступные роли и права
And позволяет изменять права согласно разрешенной модели
```

## 14. Audit log и integration log

**Связанные User Stories:** `US-MAN-014`, `US-SUP-006`, `US-ADM-004`, `US-ADM-005`  
**Связанные FR:** `FR-130`, `FR-131`, `FR-132`, `FR-133`, `FR-134`

### AC-LOG-001 — Запись действия в audit log

```gherkin
Given пользователь с правами изменяет статус документа, заявки или запроса
When изменение успешно сохраняется
Then система создает запись в audit log
And запись содержит пользователя, действие, сущность, дату и результат
```

### AC-LOG-002 — Запись интеграционного события

```gherkin
Given система получает webhook от внешней системы
When webhook обработан успешно или с ошибкой
Then система создает запись в integration log
And запись содержит внешнюю систему, тип события, external_id, статус и дату
```

### AC-LOG-003 — Ошибка API имеет trace_id

```gherkin
Given пользователь выполняет API-запрос
And на backend возникает ошибка
When система возвращает ошибку
Then ответ содержит trace_id
And trace_id можно использовать для поиска ошибки в логах
```

## 15. Поиск, фильтрация и списки

**Связанные User Stories:** `US-MAN-003`, `US-SUP-003`, `US-EMP-004`  
**Связанные FR:** `FR-053`, `FR-063`, `FR-135`, `FR-136`, `FR-137`, `FR-138`, `FR-139`, `FR-140`

### AC-LIST-001 — Пагинация списка мигрантов

```gherkin
Given в системе есть больше мигрантов, чем помещается на одну страницу
When пользователь открывает список мигрантов
Then система загружает первую страницу списка
And позволяет перейти к следующей странице
And не загружает весь список одним запросом
```

### AC-LIST-002 — Фильтрация по риску

```gherkin
Given пользователь с правами открыл список мигрантов
When пользователь выбирает фильтр по риск-статусу `Критично`
Then система показывает только мигрантов с критичным риском
```

### AC-LIST-003 — Поиск по ФИО или телефону

```gherkin
Given пользователь с правами открыл список мигрантов
When пользователь вводит ФИО или телефон в строку поиска
Then система показывает мигрантов, соответствующих запросу
```

## 16. Ограничения документа

- Acceptance Criteria не заменяют полный набор тест-кейсов.
- Детальные негативные сценарии и проверки будут описаны в разделе Testing.
- API-коды ошибок и структура response описываются в Error Model.
- Статусные модели документов, заявок, запросов и платежей описываются в Status Models.
- Критерии могут уточняться после согласования BPMN-процессов и API-контрактов.
