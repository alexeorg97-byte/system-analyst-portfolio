# Out of Scope — MigrationOS

## 1. Назначение документа

Документ фиксирует функциональность, интеграции, платформы и процессы, которые **не входят в текущий scope** проекта MigrationOS.

Out of Scope нужен, чтобы:

- защитить проект от неконтролируемого расширения требований;
- явно отделить MVP от будущих версий;
- снизить риск неверных ожиданий у бизнеса, разработки и QA;
- упростить планирование сроков и ресурсов;
- зафиксировать, какие сценарии не нужно проектировать, реализовывать и тестировать в текущей версии.

---

## 2. Принципы определения Out of Scope

Функциональность считается out of scope, если:

- не является критичной для MVP;
- требует отдельного бизнес-анализа;
- зависит от недоступной или неподтвержденной внешней интеграции;
- существенно увеличивает сложность архитектуры;
- требует отдельного юридического согласования;
- не подтверждена бизнес-заказчиком;
- может быть реализована после запуска основной версии.

## 4. Подробное описание исключений

### OOS-001 — White Label

**Что исключено:**

- отдельные бренды для разных агентств;
- разные домены и темы оформления;
- отдельные настройки интерфейса для каждого клиента;
- кастомизация логотипов, цветов и текстов;
- независимые пространства данных для нескольких агентств.

**Почему исключено:**

White Label требует полноценной multi-tenant архитектуры, расширенной модели ролей, изоляции данных, кастомизации UI и отдельного администрирования.

**Влияние на текущий проект:**

- система проектируется под одно агентство;
- работодатели являются клиентами агентства, а не отдельными владельцами платформы;
- не требуется tenant_id как обязательный разделитель всех данных;
- дизайн-система не обязана поддерживать темизацию под разные бренды.

**Условие возврата в scope:**

Функциональность может быть возвращена после подтверждения продуктовой стратегии SaaS / White Label.

---

### OOS-002 — Разработка РКЛ-робота

**Что исключено:**

- разработка RPA-робота;
- автоматизация браузерных проверок;
- парсинг государственных сайтов;
- поддержка сценариев работы робота;
- исправление ошибок SHERPA RPA.

**Почему исключено:**

SHERPA RPA рассматривается как уже существующая внешняя система. MigrationOS принимает результаты проверки, но не отвечает за сам процесс проверки.

**Влияние на текущий проект:**

- MigrationOS проектирует только входящий API / webhook для результатов РКЛ;
- ошибки робота фиксируются как интеграционные ошибки;
- система не тестирует внутреннюю работу робота;
- тестируются только входящие события, валидация payload и обработка статусов.

**Условие возврата в scope:**

Если текущий робот не сможет стабильно передавать данные, может потребоваться отдельный проект по его доработке.

---

### OOS-003 — Прямое API МВД / государственных реестров

**Что исключено:**

- прямые запросы MigrationOS к API МВД;
- официальная интеграция с государственными системами;
- автоматическая подача данных напрямую в МВД;
- получение юридически значимых статусов из государственных API.

**Почему исключено:**

Такая интеграция зависит от официального доступа, юридических регламентов, форматов обмена и ограничений государственных систем.

**Влияние на текущий проект:**

- для РКЛ используется SHERPA RPA как внешний контур;
- государственные действия могут выполняться через менеджера или внешние процессы;
- API-контракты MigrationOS не включают прямое МВД API;
- fallback-сценарии описываются отдельно.

**Условие возврата в scope:**

После подтверждения доступности официального API, юридической возможности и формата интеграции.

---

### OOS-004 — Мобильное приложение менеджера

**Что исключено:**

- отдельное iOS/Android-приложение для менеджеров агентства;
- push-задачи для менеджеров в отдельном приложении;
- мобильная обработка документов и заявок сотрудниками;
- мобильная админ-панель.

**Почему исключено:**

Основные рабочие сценарии менеджера требуют таблиц, фильтров, карточек, документов и удобнее реализуются в desktop-first админ-панели.

**Влияние на текущий проект:**

- все сценарии менеджера проектируются для web admin panel;
- мобильная адаптация админки не является обязательным MVP-требованием;
- push для менеджеров может быть заменен in-app алертами и dashboard-событиями.

**Условие возврата в scope:**

Если менеджеры действительно работают вне офиса и есть подтвержденные полевые сценарии.

---

### OOS-005 — Расширенные языки

**Что исключено:**

- таджикский язык;
- кыргызский язык;
- другие языки, кроме RU / UZ / EN;
- автоматический машинный перевод интерфейса.

**Почему исключено:**

Для MVP подтверждены RU / UZ / EN. Добавление новых языков увеличивает объем локализации, тестирования и поддержки контента.

**Влияние на текущий проект:**

- локализация проектируется расширяемой, но тестируется на RU / UZ / EN;
- новые языки не входят в acceptance criteria MVP;
- словари и шаблоны уведомлений готовятся только для выбранных языков.

**Условие возврата в scope:**

После анализа состава пользователей и подтверждения необходимости дополнительных языков.

---

### OOS-006 — Полная автоматизация всех услуг маркетплейса

**Что исключено:**

- автоматическое выполнение всех услуг без менеджера;
- индивидуальные workflow для каждой услуги;
- автоматическое формирование всех пакетов документов;
- сложная маршрутизация услуг по типам, срокам и ответственным.

**Почему исключено:**

Маркетплейс услуг требует отдельной детализации по каждой услуге: документы, условия, роли, сроки, стоимость, результат, статусы и исключения.

**Влияние на текущий проект:**

- MVP поддерживает каталог услуг и создание заявки;
- часть услуг обрабатывается вручную менеджером;
- статусы заявок фиксируются в системе;
- сложная автоматизация услуг не входит в базовый scope.

**Условие возврата в scope:**

После подготовки отдельного ТЗ на маркетплейс и приоритизации услуг.

---

### OOS-007 — Продвинутая AI-аналитика

**Что исключено:**

- ML-модели прогнозирования нарушений;
- автоматическое предсказание вероятности просрочки;
- сложные рекомендательные модели;
- обучение моделей на исторических данных;
- explainable AI для риск-решений.

**Почему исключено:**

Для первой версии достаточно rule-based риск-скора на основе сроков документов, РКЛ-статуса и истории нарушений. ML требует качественных данных и отдельной проверки гипотез.

**Влияние на текущий проект:**

- риск-скор считается по прозрачным правилам;
- AI не является критичной зависимостью MVP;
- acceptance criteria не проверяют качество ML-модели.

**Условие возврата в scope:**

После накопления данных, постановки ML-гипотез и подтверждения бизнес-эффекта.

---

### OOS-008 — Полноценный BI-модуль

**Что исключено:**

- конструктор отчетов;
- кастомные дашборды;
- свободная настройка метрик пользователями;
- сложные выгрузки и визуализации;
- полноценный BI-layer.

**Почему исключено:**

BI требует отдельной модели метрик, витрин данных и согласования управленческой отчетности.

**Влияние на текущий проект:**

- в MVP достаточно базовых дашбордов по рискам, заявкам и статусам;
- кастомные отчеты не входят в функциональные требования MVP;
- аналитика ограничивается заранее определенными показателями.

**Условие возврата в scope:**

После запуска MVP и сбора требований руководителей к отчетности.

---

### OOS-009 — Юридически значимая электронная подпись

**Что исключено:**

- интеграция с провайдером ЭП;
- выпуск сертификатов;
- юридически значимое подписание документов;
- проверка подписи;
- долгосрочное хранение юридически значимых подписанных документов.

**Почему исключено:**

ЭП требует отдельной юридической модели, выбора провайдера, договоров, интеграций и регламентов.

**Влияние на текущий проект:**

- PDF-документы могут формироваться и храниться;
- подписание может быть представлено как будущий сценарий;
- юридически значимая ЭП не входит в MVP acceptance criteria.

**Условие возврата в scope:**

После выбора провайдера ЭП и согласования юридического процесса.

---

### OOS-010 — SEO и рекламное продвижение лендинга

**Что исключено:**

- SEO-стратегия;
- рекламные кампании;
- контент-маркетинг;
- аналитика рекламных каналов;
- продвижение в поисковых системах.

**Почему исключено:**

Лендинг входит в продуктовый контур как публичная точка входа, но продвижение относится к маркетингу, а не к системной функциональности платформы.

**Влияние на текущий проект:**

- проектируются базовые страницы лендинга;
- формы заявок и контентные блоки могут входить в MVP;
- SEO и рекламные метрики не входят в системные требования.

**Условие возврата в scope:**

В рамках отдельного маркетингового проекта.

---

### OOS-011 — Постзапусковой SLA поддержки

**Что исключено:**

- регламенты L1/L2/L3;
- время реакции на инциденты;
- матрица эскалации поддержки;
- договорной SLA;
- процессы поддержки после запуска.

**Почему исключено:**

SLA поддержки требует отдельной организационной модели и договоренностей между бизнесом, техподдержкой и эксплуатацией.

**Влияние на текущий проект:**

- технические NFR по доступности и мониторингу фиксируются отдельно;
- операционный SLA поддержки не входит в MVP;
- support-процессы могут быть подготовлены после запуска.

**Условие возврата в scope:**

После определения модели эксплуатации и поддержки продукта.

---

### OOS-012 — Полная замена 1С

**Что исключено:**

- бухгалтерский учет;
- кадровый учет;
- налоговый учет;
- расчет зарплаты;
- замена учетных процессов 1С;
- перенос всех учетных данных в MigrationOS как master system.

**Почему исключено:**

1С остается учетной системой. MigrationOS работает как операционная платформа миграционного сопровождения и интегрируется с 1С по согласованному набору данных.

**Влияние на текущий проект:**

- MigrationOS не становится основной бухгалтерской системой;
- интеграция с 1С ограничивается согласованными сущностями;
- финансовые и кадровые процессы остаются за пределами платформы.

**Условие возврата в scope:**

Только в рамках отдельного проекта по трансформации учетной архитектуры.

---

### OOS-013 — Мультиарендность / tenant model

**Что исключено:**

- независимые tenant-пространства;
- разные агентства в одной платформе;
- отдельные настройки, роли и данные для каждого tenant;
- tenant-level billing;
- tenant-level admin.

**Почему исключено:**

MVP проектируется под одно агентство и его клиентов. Полная tenant model значительно меняет архитектуру данных, безопасность и администрирование.

**Влияние на текущий проект:**

- работодатель не считается tenant-владельцем платформы;
- employer_id используется для ограничения видимости данных работодателя;
- tenant_id не является обязательным сквозным идентификатором всех сущностей.

**Условие возврата в scope:**

Если продукт развивается как SaaS-платформа для нескольких агентств.

---

### OOS-014 — Офлайн-режим с полноценной синхронизацией

**Что исключено:**

- создание заявок без интернета;
- редактирование данных офлайн;
- очередь офлайн-операций;
- разрешение конфликтов после синхронизации;
- хранение полного профиля офлайн.

**Почему исключено:**

Полноценный offline-first режим требует сложной синхронизации, conflict resolution и дополнительных требований к безопасности локального хранения.

**Влияние на текущий проект:**

- приложение может показывать error/empty/offline states;
- критичные действия требуют соединения с backend;
- полноценная офлайн-синхронизация не тестируется в MVP.

**Условие возврата в scope:**

После анализа реальных сценариев использования без интернета.

---

### OOS-015 — Продвинутая маршрутизация задач

**Что исключено:**

- автоматическое распределение задач по загрузке менеджеров;
- маршрутизация по навыкам;
- SLA-based assignment;
- автоматический rebalancing очереди;
- сложные правила приоритизации.

**Почему исключено:**

Для MVP достаточно ручного назначения ответственного и базового статуса задачи или заявки.

**Влияние на текущий проект:**

- система может позволять назначить ответственного;
- автоматическая балансировка нагрузки не проектируется;
- метрики загрузки менеджеров могут быть собраны позже.

**Условие возврата в scope:**

После накопления данных о нагрузке и подтверждения проблемы распределения задач.

## 5. Влияние Out of Scope на проектирование

| Область | Как влияет Out of Scope |
|---|---|
| Требования | Исключенные функции не попадают в FR, NFR, AC и тест-кейсы MVP |
| Архитектура | Не проектируется tenant model, White Label, полноценный BI-layer и offline-first синхронизация |
| API | Не создаются endpoint для прямого МВД API, ML-моделей, tenant management и юридически значимой ЭП |
| UI | Не проектируются экраны менеджерского мобильного приложения, White Label-настройки и BI-конструктор |
| QA | Исключенные сценарии не входят в обязательную приемку MVP |
| DevOps | Не требуется инфраструктура для multi-tenant SaaS и production SLA поддержки на этапе MVP |
| Аналитика | Исключенные функции могут быть оформлены как backlog / future scope |

## 6. Future Scope

Функции, исключенные из текущего scope, могут быть возвращены в будущих версиях после отдельного анализа.

| Направление | Возможная будущая версия |
|---|---|
| White Label / SaaS | Версия для нескольких агентств |
| Расширенные языки | Добавление TJ / KG и других языков |
| AI-аналитика | ML-прогнозирование рисков после накопления данных |
| BI | Конструктор отчетов и управленческие витрины |
| Электронная подпись | Интеграция с провайдером юридически значимой ЭП |
| Менеджерское мобильное приложение | Мобильная работа сотрудников агентства |
| Offline-first | Очередь офлайн-действий и последующая синхронизация |
| Расширенный маркетплейс | Автоматизация отдельных услуг по отдельным workflow |
| SLA поддержки | Регламенты эксплуатации и поддержки после запуска |
