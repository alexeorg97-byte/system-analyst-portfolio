# Role Model — MigrationOS

## 1. Назначение документа

Документ описывает ролевую модель платформы MigrationOS.

Ролевая модель определяет:

- какие роли существуют в системе;
- какие пользователи относятся к каждой роли;
- какие бизнес-задачи решает каждая роль;
- какие модули доступны каждой роли;
- какие данные видит каждая роль;
- какие ограничения доступа должны учитываться при проектировании API, UI, ERD и тест-кейсов.

Документ является основой для:

- матрицы доступа;
- проектирования backend authorization;
- проектирования интерфейсов;
- подготовки acceptance criteria;
- тестирования прав доступа;
- описания audit log.

---

## 2. Принципы ролевой модели

Ролевая модель MigrationOS строится на следующих принципах:

- доступ к данным определяется ролью пользователя;
- доступ к данным должен проверяться на backend;
- frontend не считается надежным механизмом ограничения доступа;
- работодатель видит только мигрантов своей организации;
- мигрант видит только собственный профиль и связанные данные;
- агентство имеет операционный доступ к данным мигрантов и работодателей;
- руководитель агентства имеет расширенный доступ к аналитике и рискам;
- superadmin управляет системными настройками, ролями и пользователями;
- действия с критичными сущностями должны попадать в audit log;
- попытка доступа к запрещенным данным должна возвращать ошибку доступа.

## 3. Список ролей

| Системная роль | Название в интерфейсе | Тип пользователя | Основной канал | Краткое описание |
|---|---|---|---|---|
| `migrant` | Мигрант | Внешний пользователь | Мобильное приложение | Видит свои документы, заявки, запросы, уведомления и чат |
| `employer` | Работодатель | Внешний пользователь / клиент | Веб-кабинет работодателя | Видит только мигрантов своей организации, риски, запросы, заявки и платежи |
| `manager` | Менеджер агентства | Внутренний пользователь | Админ-панель | Обрабатывает документы, заявки, запросы, чаты и задачи |
| `supervisor` | Руководитель агентства | Внутренний пользователь | Админ-панель | Контролирует риски, аналитику, проекты, работодателей и эффективность процессов |
| `superadmin` | Системный администратор | Внутренний технический пользователь | Админ-панель | Управляет пользователями, ролями, справочниками и системными настройками |

## 4. Роль `migrant`

### 4.1. Описание

`migrant` — внешний конечный пользователь, иностранный работник, находящийся на сопровождении агентства или работодателя.

Основной интерфейс роли — мобильное приложение.

### 4.2. Цели роли

- видеть свои персональные данные;
- видеть свои документы и сроки действия;
- загружать сканы документов;
- получать уведомления о сроках и статусах;
- создавать запросы работодателю или агентству;
- заказывать услуги;
- отслеживать статус заявок;
- общаться с менеджером агентства.

### 4.3. Доступные модули

| Модуль | Доступ |
|---|---|
| Мобильное приложение | Да |
| Профиль мигранта | Только свой |
| Документы | Только свои |
| Запросы | Только свои |
| Маркетплейс услуг | Да |
| Уведомления | Только свои |
| Чат | Только свои диалоги |
| ЛК работодателя | Нет |
| Админ-панель | Нет |
| Управление пользователями | Нет |
| Системные настройки | Нет |

### 4.4. Правила видимости данных

Мигрант может видеть:

- свой профиль;
- свои документы;
- свои файлы документов;
- свои заявки;
- свои запросы;
- свои уведомления;
- свои сообщения в чате;
- доступные ему услуги.

Мигрант не может видеть:

- других мигрантов;
- работодателей, кроме ограниченной информации, если она нужна по сценарию;
- данные других организаций;
- внутренние комментарии менеджеров;
- audit log;
- integration log;
- системные настройки.

### 4.5. Ограничения

- мигрант не может менять критичные данные без проверки агентства, если такое правило включено;
- мигрант не может вручную менять статус документа, заявки или запроса;
- мигрант не может получить доступ к чужим данным прямым API-запросом;
- мигрант не может видеть технические ошибки интеграций.

## 5. Роль `employer`

### 5.1. Описание

`employer` — внешний пользователь, представитель компании-работодателя, которая взаимодействует с агентством и контролирует своих мигрантов.

Основной интерфейс роли — веб-кабинет работодателя.

### 5.2. Цели роли

- видеть список своих мигрантов;
- контролировать документы и сроки;
- видеть риск-дашборд;
- обрабатывать запросы от мигрантов;
- заказывать услуги агентства;
- видеть счета и платежи;
- общаться с менеджером агентства;
- снижать юридические и операционные риски.

### 5.3. Доступные модули

| Модуль | Доступ |
|---|---|
| ЛК работодателя | Да |
| Список мигрантов | Только мигранты своей организации |
| Карточка мигранта | Только просмотр и только свои мигранты |
| Документы мигранта | Только просмотр и только свои мигранты |
| Риск-дашборд | Только по своей организации |
| Запросы мигрантов | Только связанные со своей организацией |
| Маркетплейс услуг | Да |
| Счета и платежи | Только своей организации |
| Чат | Только свои диалоги |
| Админ-панель | Нет |
| Управление ролями | Нет |
| Integration log | Нет |
| Audit log | Нет |

### 5.4. Правила видимости данных

Работодатель может видеть:

- свою организацию;
- пользователей своей организации;
- мигрантов, связанных с его организацией;
- документы своих мигрантов в режиме просмотра;
- риск-статусы своих мигрантов;
- запросы, связанные со своими мигрантами;
- заявки и платежи своей организации;
- сообщения в своих диалогах.

Работодатель не может видеть:

- мигрантов других работодателей;
- документы чужих мигрантов;
- внутренние комментарии агентства, если они не предназначены клиенту;
- данные других организаций;
- системные роли и настройки;
- audit log;
- integration log.

### 5.5. Ограничения

- работодатель не является tenant-владельцем платформы;
- работодатель не управляет глобальными настройками;
- работодатель не может редактировать карточку мигранта без отдельного разрешения;
- работодатель не может изменять риск-статус;
- работодатель не может подтверждать РКЛ-результаты;
- прямой API-запрос к чужому мигранту должен возвращать 403 Forbidden.

## 6. Роль `manager`

### 6.1. Описание

`manager` — внутренний пользователь агентства, который выполняет операционную работу: ведет мигрантов, документы, заявки, запросы, чаты и задачи.

Основной интерфейс роли — админ-панель.

### 6.2. Цели роли

- вести карточки мигрантов;
- проверять и обновлять документы;
- обрабатывать заявки на услуги;
- обрабатывать запросы мигрантов и работодателей;
- видеть риски и приоритеты;
- общаться с мигрантами и работодателями;
- фиксировать изменения в системе;
- снижать количество ручной коммуникации вне платформы.

### 6.3. Доступные модули

| Модуль | Доступ |
|---|---|
| Админ-панель | Да |
| Список мигрантов | Согласно назначению или правилам агентства |
| Карточка мигранта | Согласно назначению или правилам агентства |
| Документы | Просмотр и обработка согласно правам |
| Заявки | Просмотр и обработка согласно правам |
| Запросы | Просмотр и обработка согласно правам |
| Чаты | Диалоги, связанные с доступными сущностями |
| Задачи | Да |
| Работодатели | Просмотр / обработка согласно правам |
| Проекты | Просмотр согласно правам |
| Риск-дашборд | Операционный уровень |
| Audit log | Ограниченный просмотр по доступным сущностям |
| Integration log | Ограниченный просмотр ошибок, если разрешено |
| Управление ролями | Нет |
| Системные настройки | Нет |

### 6.4. Правила видимости данных

Менеджер может видеть:

- мигрантов, назначенных ему или доступных по правилам агентства;
- документы этих мигрантов;
- заявки и запросы, назначенные ему или доступные по очереди;
- чаты по доступным мигрантам, заявкам и работодателям;
- статусы документов, заявок, запросов и рисков;
- историю действий по доступным сущностям;
- интеграционные ошибки, если это разрешено ролью.

Менеджер не может:

- управлять глобальными ролями;
- изменять системные настройки;
- видеть данные, ограниченные уровнем supervisor / superadmin;
- обходить правила доступа прямыми API-запросами;
- удалять критичные данные без audit trail.

### 6.5. Ограничения

- действия менеджера с документами, заявками, запросами и статусами должны логироваться;
- смена статуса должна соответствовать статусной модели;
- менеджер не может менять данные чужой зоны ответственности, если такая зона закреплена;
- менеджер не может отключать audit log или integration log.

---

## 7. Роль `supervisor`

### 7.1. Описание

`supervisor` — руководитель агентства или старший пользователь, который контролирует операционную картину, риски, аналитику, проекты, работодателей и эффективность процессов.

Основной интерфейс роли — админ-панель.

### 7.2. Цели роли

- видеть всех мигрантов агентства;
- контролировать критичные риски;
- анализировать документы, заявки и запросы;
- смотреть аналитику по проектам и работодателям;
- контролировать эффективность менеджеров;
- видеть проблемные интеграции;
- принимать управленческие решения.

### 7.3. Доступные модули

| Модуль | Доступ |
|---|---|
| Админ-панель | Да |
| Все мигранты | Да |
| Все работодатели | Да |
| Проекты | Да |
| Документы | Просмотр / контроль согласно политике |
| Заявки и запросы | Да |
| Риск-дашборд | Полный доступ |
| Аналитика | Да |
| Задачи менеджеров | Да |
| Чаты | Просмотр согласно политике |
| Audit log | Расширенный просмотр |
| Integration log | Расширенный просмотр |
| Управление пользователями | Ограниченно, если разрешено |
| Управление ролями | Нет / ограниченно |
| Системные настройки | Нет |

### 7.4. Правила видимости данных

Supervisor может видеть:

- всех мигрантов агентства;
- всех работодателей;
- проекты и связанные с ними данные;
- риск-дашборды;
- аналитику по мигрантам, документам, заявкам и работодателям;
- critical alerts;
- audit log по критичным действиям;
- integration log по внешним событиям.

Supervisor не должен:

- управлять низкоуровневыми системными настройками;
- менять модель ролей без superadmin;
- отключать audit log;
- получать доступ к техническим секретам;
- выполнять действия superadmin без отдельного разрешения.

### 7.5. Ограничения

- доступ supervisor шире, чем у manager, но не равен superadmin;
- действия supervisor также должны логироваться;
- доступ к чувствительным документам может быть ограничен политикой compliance;
- аналитика должна учитывать права и бизнес-ограничения.

## 8. Роль `superadmin`

### 8.1. Описание

`superadmin` — технический или системный администратор платформы, отвечающий за пользователей, роли, справочники и настройки.

Основной интерфейс роли — админ-панель.

### 8.2. Цели роли

- управлять пользователями;
- управлять ролями и правами;
- настраивать справочники;
- контролировать системные настройки;
- видеть audit log и integration log;
- поддерживать корректность ролевой модели.

### 8.3. Доступные модули

| Модуль | Доступ |
|---|---|
| Админ-панель | Да |
| Пользователи | Полный доступ |
| Роли и права | Полный доступ |
| Справочники | Полный доступ |
| Системные настройки | Полный доступ |
| Audit log | Полный доступ |
| Integration log | Полный доступ |
| Мигранты | Технический доступ согласно политике |
| Работодатели | Технический доступ согласно политике |
| Документы | Технический доступ согласно политике |
| Аналитика | Да |
| Платежи | Просмотр согласно политике |
| Чаты | Ограниченный технический доступ согласно политике |

### 8.4. Правила видимости данных

Superadmin может:

- создавать и блокировать пользователей;
- назначать роли;
- управлять справочниками;
- управлять системными настройками;
- просматривать audit log;
- просматривать integration log;
- расследовать технические ошибки.

Superadmin не должен:

- использовать технический доступ для операционной обработки миграционных кейсов без необходимости;
- менять бизнес-статусы вне регламентов;
- обходить требования compliance;
- удалять критичные данные без audit trail.

### 8.5. Ограничения

- действия superadmin должны логироваться;
- доступ superadmin должен быть защищен 2FA;
- управление ролями должно быть ограничено только этой ролью или отдельным разрешением;
- доступ к production-данным должен быть регламентирован.

## 10. Ключевые правила backend authorization

| ID | Правило |
|---|---|
| AUTHZ-001 | Любой защищенный API-запрос должен проверять наличие авторизации |
| AUTHZ-002 | Роль пользователя должна проверяться на backend |
| AUTHZ-003 | Доступ к конкретной сущности должен проверяться не только по роли, но и по контексту |
| AUTHZ-004 | `migrant` может получать только сущности, связанные со своим `migrant_id` |
| AUTHZ-005 | `employer` может получать только сущности, связанные со своим `employer_id` |
| AUTHZ-006 | `manager` получает доступ согласно назначению, проекту или правилам агентства |
| AUTHZ-007 | `supervisor` получает расширенный доступ в рамках агентства |
| AUTHZ-008 | `superadmin` получает административный доступ согласно политике |
| AUTHZ-009 | Попытка доступа к чужой сущности должна возвращать 403 Forbidden |
| AUTHZ-010 | Ошибка доступа не должна раскрывать наличие или отсутствие запрещенной сущности, если это может привести к утечке |
| AUTHZ-011 | Все изменения ролей и прав должны логироваться |
| AUTHZ-012 | Действия с документами, платежами, заявками и риск-статусами должны логироваться |

## 11. Ролевые ограничения для UI

| Правило | Описание |
|---|---|
| UI-ROLE-001 | UI должен скрывать недоступные разделы для роли пользователя |
| UI-ROLE-002 | UI не должен показывать кнопки действий, которые пользователь не может выполнить |
| UI-ROLE-003 | UI-ограничения не заменяют backend-проверку доступа |
| UI-ROLE-004 | Если действие запрещено backend, frontend должен показать понятное сообщение |
| UI-ROLE-005 | Для разных ролей могут использоваться разные стартовые экраны |
| UI-ROLE-006 | Списки и фильтры должны показывать только доступные пользователю данные |
| UI-ROLE-007 | Работодатель не должен видеть элементы интерфейса агентства |
| UI-ROLE-008 | Мигрант не должен видеть служебные статусы, если они не предназначены для пользователя |

## 12. Потенциальные конфликтные сценарии

| Сценарий | Риск | Ожидаемое правило |
|---|---|---|
| Работодатель пытается открыть чужого мигранта по прямому URL | Утечка ПДн | Backend возвращает 403 Forbidden |
| Мигрант пытается получить чужой документ через API | Утечка документа | Backend возвращает 403 Forbidden |
| Менеджер пытается изменить заявку вне зоны ответственности | Нарушение процесса | Доступ запрещен или требуется расширенное право |
| Supervisor пытается изменить системные настройки | Ошибка конфигурации | Доступ запрещен без superadmin |
| Superadmin меняет роль пользователя | Риск эскалации прав | Действие логируется в audit log |
| Пользователь видит кнопку действия, но backend запрещает операцию | Непоследовательный UX | UI должен быть синхронизирован с permissions |
| Работодатель видит внутренний комментарий менеджера | Утечка внутренней информации | Комментарии разделяются на internal/external |
| Ошибка доступа раскрывает существование чужой сущности | Информационная утечка | Возвращается безопасная ошибка без лишних деталей |
