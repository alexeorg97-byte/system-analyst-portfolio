# Data Dictionary — MigrationOS

## 1. Назначение документа

Документ описывает словарь данных платформы MigrationOS.

Data Dictionary нужен, чтобы:

- зафиксировать поля ключевых сущностей;
- описать типы данных и обязательность;
- определить уникальные поля и бизнес-валидации;
- согласовать терминологию между аналитиком, backend, frontend, QA и бизнесом;
- подготовить основу для SQL schema, API-контрактов и тест-кейсов.

Документ является продолжением:

- [ERD](./erd.md)
- [Entities](./entities.md)

---

## 2. Принципы описания данных

| Принцип | Описание |
|---|---|
| Логический уровень | Документ описывает данные на уровне бизнес- и системной логики |
| SQL отдельно | Индексы, constraints и DDL будут описаны в `schema.sql` |
| UUID как идентификатор | Основные сущности используют UUID |
| Enum для статусов | Статусы должны быть ограничены допустимыми значениями |
| Auditability | Критичные изменения должны быть трассируемыми |
| Security by design | ПДн, документы и платежи требуют ограниченного доступа |
| Idempotency | Webhook-события должны иметь идентификаторы для защиты от дублей |

## 3. Общие поля

Эти поля могут использоваться в большинстве сущностей.

| Поле | Тип данных | Обязательное | Уникальное | Описание | Валидация |
|---|---|---:|---:|---|---|
| `id` | UUID | Да | Да | Уникальный идентификатор записи | Генерируется системой |
| `created_at` | datetime | Да | Нет | Дата создания записи | Заполняется системой |
| `updated_at` | datetime | Нет | Нет | Дата последнего обновления | Обновляется системой |
| `created_by` | UUID | Нет | Нет | Пользователь, создавший запись | Должен ссылаться на `User.id` |
| `updated_by` | UUID | Нет | Нет | Пользователь, изменивший запись | Должен ссылаться на `User.id` |
| `status` | enum | Да | Нет | Текущий статус сущности | Значение из допустимого enum |

Примечание:

- поле `updated_at` может отсутствовать у append-only сущностей;
- поле `status` не является обязательным для всех таблиц, но используется в большинстве бизнес-сущностей.

## 25. Правила для ПДн, audit/integration logs и чувствительных файлов

### 25.1. ПДн

| Правило | Описание |
|---|---|
| Минимизация | В API и UI должны возвращаться только необходимые поля |
| Разграничение доступа | ПДн мигранта доступны только по контекстам `own`, `org`, `assigned`, `agency` |
| Логирование доступа | Критичные действия с ПДн должны попадать в audit log |
| Безопасные ошибки | Ошибки доступа не должны раскрывать наличие чужих данных |

### 25.2. AuditLog

| Правило | Описание |
|---|---|
| Append-only | Записи не редактируются и не удаляются штатным пользовательским сценарием |
| Ограниченный состав данных | Не хранить полные чувствительные поля без необходимости |
| Трассируемость | Должны сохраняться `actor`, `action`, `entity_type`, `entity_id`, `created_at` |

### 25.3. IntegrationLog

| Правило | Описание |
|---|---|
| Идемпотентность | Внешние `event_id` используются для защиты от дублей |
| Ограничение payload | Raw payload хранится только при необходимости и с учетом безопасности |
| Расследуемость | Должны сохраняться `integration_name`, `direction`, `status`, связанная сущность и время |

### 25.4. Чувствительные файлы

| Правило | Описание |
|---|---|
| Нет публичных URL | `storage_key` не является публичной ссылкой |
| Временный доступ | Файл выдается через presigned URL или защищенный backend-контур |
| Валидация загрузки | Размер, MIME-тип и бизнес-тип документа проверяются backend |
| Логирование | Просмотр, скачивание, подтверждение и отклонение файлов могут логироваться |
