# Project Story — MigrationOS

## 1. Назначение документа

Документ помогает подготовить рассказ о портфолио-кейсе MigrationOS для собеседования на позицию системного аналитика.

Project Story нужен, чтобы:

- быстро объяснить, что это за проект;
- показать роль системного аналитика;
- связать артефакты портфолио в единую историю;
- подготовить короткие и развернутые версии рассказа;
- не путать портфолио-кейс с коммерческим опытом;
- уверенно отвечать на вопросы интервьюера.

## 3. Краткое описание проекта

MigrationOS — это концепт цифровой платформы для сопровождения миграционного учета, документооборота, сервисных операций и контроля рисков при работе с иностранной рабочей силой.

В системе есть несколько пользовательских контуров:

- мобильное приложение мигранта;
- кабинет работодателя;
- административная панель агентства;
- публичный landing;
- backend API;
- интеграции с внешними системами;
- документы, запросы, платежи, уведомления, РКЛ-проверки и риск-скоринг.

MigrationOS — это портфолио-кейс, в котором я отработал полный цикл системного анализа на примере платформы для миграционного учета и сопровождения иностранных работников.

Для меня этот проект важен тем, что он показывает не отдельный навык, а системное мышление: как связать требования, данные, API, интеграции, роли, тестирование и архитектуру в единый продуктовый контекст.

## 7. Рассказ на 3 минуты

MigrationOS — это учебно-практический портфолио-кейс системного аналитика. Я выбрал предметную область миграционного учета, потому что в ней много типичных для системного анализа сложностей: несколько ролей, чувствительные персональные данные, документооборот, внешние интеграции, статусы, платежи, уведомления, риски и административный контур.

Сначала я описал продуктовую рамку: зачем нужна система, какие проблемы она решает, кто стейкхолдеры, что входит в MVP и что остается вне scope. Затем перешел к требованиям: бизнес-требованиям, функциональным требованиям, NFR, user stories и acceptance criteria.

После этого я отдельно проработал роли и доступы. Для меня это был важный блок, потому что в системе есть внешние пользователи и внутренние сотрудники агентства. Мигрант должен видеть только свои данные, работодатель — только своих мигрантов, manager работает с операционными задачами, supervisor — с критичными рисками, superadmin — с ролями и настройками.

Дальше я описал процессы: регистрацию мигранта, загрузку документа, РКЛ-проверку, заказ услуги, запрос работодателя. Потом перешел к модели данных: ERD, сущности, словарь данных, статусные модели и SQL-примеры.

Следующий большой блок — API и интеграции. Я подготовил OpenAPI-спецификацию, описал error model, request service API, payment webhook и RKL webhook. По интеграциям отдельно разобрал SHERPA RPA, 1C, SBP, FCM, S3 и `IntegrationLog`.

Также я сделал UI-сценарии для mobile app, employer cabinet, admin panel и landing, а затем тестовый блок: test strategy, test cases, checklist и acceptance testing.

В конце я оформил архитектурный блок: architecture overview, C4 context, C4 container, sequence diagrams и deployment context. Этот блок показывает, как пользовательские сценарии связаны с backend-сервисами, БД, S3, внешними системами, логами, мониторингом и deployment-подходом.

## 8. Рассказ на 5 минут

MigrationOS — это мой портфолио-кейс, который я сделал как полноценный пакет системного анализа. Я не позиционирую его как коммерческий production-опыт, но он построен так, чтобы показать ход мыслей системного аналитика в реальном продукте.

Предметная область — платформа для сопровождения миграционного учета и иностранных работников. В системе есть несколько контуров: мобильное приложение мигранта, кабинет работодателя, административная панель агентства и публичный landing. Основные процессы: регистрация, профиль, согласие на ПДн, загрузка документов, проверка документов, запросы, заказ услуг, оплата, уведомления, РКЛ-проверки и контроль рисков.

Я начал с верхнего уровня: product vision, project scope, stakeholders, assumptions and constraints, glossary. Это позволило определить границы проекта и договориться, что система делает, а что не делает. Например, я явно вынес из scope разработку RPA-робота SHERPA и прямой API МВД, чтобы не смешивать ответственность платформы и внешних систем.

После этого я проработал требования. В functional requirements я описал основные модули, в non-functional requirements — производительность, безопасность, доступность, хранение ПДн, наблюдаемость и интеграционные требования. User stories и acceptance criteria помогли связать требования с проверяемыми сценариями.

Дальше я сделал блок ролей и доступов. Это один из самых важных блоков, потому что система работает с персональными данными и документами. Я описал роли `migrant`, `employer`, `manager`, `supervisor`, `superadmin`, матрицу доступа и permissions. Ключевой принцип: frontend ничего не решает сам, все object-level permissions проверяются на backend.

Затем я описал процессы и данные. В процессах есть регистрация, загрузка документов, РКЛ-проверка, заказ услуги и запрос работодателя. В модели данных есть ERD, data dictionary, status models и SQL-примеры. Я отдельно проработал статусы документов, платежей, запросов, заказов услуг и интеграционных событий, потому что именно статусные переходы часто становятся источником ошибок.

После этого я перешел к API. Я подготовил API overview, OpenAPI, request service API, RKL webhook, payment webhook и error model. Важное решение: payment status подтверждается только webhook от провайдера, а frontend redirect не меняет статус оплаты. Это снижает финансовый риск.

Большой блок — интеграции. Я описал SHERPA RPA для РКЛ-проверок, 1C для обмена учетными данными, SBP/payment provider для оплат, FCM для push, S3 для файлов и `IntegrationLog` как единый журнал интеграционных событий. Для S3 я зафиксировал, что объектное хранилище не принимает решение о доступе: backend проверяет permission и только потом выдает временный URL.

Потом я сделал UI-сценарии и edge cases: отдельно для mobile app, employer cabinet, admin panel и landing. После этого — тестирование: test strategy, test cases, QA checklist и acceptance testing. Это помогает показать, что требования не просто описаны, а проверяемы.

В финале я оформил архитектуру: architecture overview, C4 context, C4 container, sequence diagrams и deployment context. Там видно, как frontend, API Gateway, FastAPI-сервисы, PostgreSQL, Redis, S3, внешние системы, `IntegrationLog`, `AuditLog`, Prometheus/Grafana и Kubernetes складываются в общую картину.

Главная ценность этого кейса — он показывает end-to-end мышление системного аналитика: от бизнес-контекста и требований до API, данных, интеграций, тестирования и архитектуры.

## 11. Какие решения принимал и почему

| Решение | Почему |
|---|---|
| Разделить роли `migrant` / `employer` / `internal users` | У разных ролей разные зоны доступа и риски |
| Проверять object-level permissions на backend | Frontend нельзя считать источником истины |
| Подтверждать оплату только webhook | Redirect ненадежен как финансовое подтверждение |
| Хранить binary-файлы в S3 | БД не должна хранить тяжелые документы |
| Выдавать файлы через presigned URL | Нужен временный контролируемый доступ |
| Логировать интеграции в `IntegrationLog` | Нужно расследовать webhooks, retries, duplicates |
| Логировать ручные действия в `AuditLog` | Нужна операционная и юридическая трассируемость |
| Не делать weak RKL match автоматически | Ошибочное сопоставление может привести к серьезным последствиям |
| Разделить test cases и checklist | Подробные тесты и быстрые проверки решают разные задачи |
| Сделать C4 и sequence diagrams | Архитектуру удобнее объяснять через уровни и сценарии |

## 14. Как не переиграть и не соврать на собеседовании

Важно говорить честно:

- это портфолио-кейс, а не рабочий production-проект;
- я не внедрял систему у реального клиента;
- я не управлял командой разработки в рамках этого проекта;
- часть решений — проектные допущения;
- некоторые интеграции описаны на уровне аналитического проектирования, а не реального подключения;
- ценность кейса — в аналитической проработке, структуре и связности артефактов.

Хорошая формулировка:

> “Я не хочу выдавать этот проект за коммерческий опыт. Это портфолио-кейс, который я сделал, чтобы показать, как я мыслю как системный аналитик: от требований и ролей до API, данных, интеграций, тестирования и архитектуры.”

### 14.1. Чего лучше избегать

- не говорить “мы внедрили”, если внедрения не было;
- не говорить “я руководил разработкой”, если это не так;
- не утверждать, что интеграции реально подключались к production-контурам;
- не выдавать архитектурные решения за факт промышленной эксплуатации;
- не пытаться “додумать” коммерческие детали, которых в кейсе нет.
