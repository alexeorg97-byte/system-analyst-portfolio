# User Stories

## US-001

**User Story:** Как посетитель сайта, я хочу оставить заявку через форму, чтобы со мной могли связаться без звонка по телефону.  
**Acceptance Criteria:**  
- форма доступна на лендинге  
- обязательные поля валидируются  
- после отправки заявка сохраняется в системе

## US-002

**User Story:** Как посетитель сайта, я хочу задать вопрос в чат-виджете, чтобы получить помощь, не покидая страницу.  
**Acceptance Criteria:**  
- чат открывается на публичном сайте  
- диалог начинается с bot-сообщения  
- история текущей сессии сохраняется

## US-003

**User Story:** Как посетитель сайта, я хочу позвать оператора, чтобы продолжить общение с человеком.  
**Acceptance Criteria:**  
- в чате есть действие вызова оператора  
- после запроса статус сессии меняется на `waiting_operator`  
- сценарные quick replies скрываются

## US-004

**User Story:** Как посетитель сайта, я хочу видеть ответы оператора отдельно от сообщений бота, чтобы не путаться в диалоге.  
**Acceptance Criteria:**  
- сообщения оператора визуально выделены  
- над сообщением есть подпись оператора  
- длинные сообщения корректно переносятся

## US-005

**User Story:** Как посетитель сайта, я хочу продолжить чат после обновления страницы, чтобы не терять историю диалога.  
**Acceptance Criteria:**  
- сессия восстанавливается по сохранённому идентификатору  
- история загружается из API  
- статус чата сохраняется

## US-006

**User Story:** Как оператор, я хочу видеть список чат-сессий, чтобы быстро брать в работу обращения пользователей.  
**Acceptance Criteria:**  
- админка показывает список чатов  
- видны статус, оператор и последнее сообщение  
- можно открыть детальную страницу чата

## US-007

**User Story:** Как оператор, я хочу отвечать пользователю в real-time режиме, чтобы вести живой диалог.  
**Acceptance Criteria:**  
- сообщение из админки приходит visitor без перезагрузки  
- сообщение сохраняется в БД  
- при первом ответе статус меняется на `operator_replied`

## US-008

**User Story:** Как оператор, я хочу закрыть чат, чтобы завершить работу по неактуальному диалогу.  
**Acceptance Criteria:**  
- оператор может закрыть чат из админки  
- visitor получает уведомление  
- новые сообщения в сессию больше не принимаются

## US-009

**User Story:** Как оператор, я хочу менять статус лида, чтобы отражать текущую стадию обработки.  
**Acceptance Criteria:**  
- доступны разрешённые статусы  
- изменение сохраняется  
- событие фиксируется в истории и аудите

## US-010

**User Story:** Как оператор, я хочу оставлять внутренние комментарии, чтобы передавать контекст другим сотрудникам.  
**Acceptance Criteria:**  
- комментарий сохраняется у лида  
- комментарий доступен в карточке заявки  
- добавление отражается в `LeadEvent`

## US-011

**User Story:** Как администратор, я хочу управлять пользователями админки, чтобы выдавать и отзывать доступ без изменения БД вручную.  
**Acceptance Criteria:**  
- есть список пользователей  
- можно создать нового пользователя  
- можно изменить роль и активность

## US-012

**User Story:** Как администратор, я хочу сбрасывать пароль пользователя, чтобы восстановить доступ сотруднику.  
**Acceptance Criteria:**  
- доступна отдельная форма сброса пароля  
- пароль хэшируется  
- факт сброса отражается в аудите

## US-013

**User Story:** Как администратор, я хочу видеть аудит действий, чтобы понимать, кто и когда изменял данные в системе.  
**Acceptance Criteria:**  
- журнал показывает пользователя, action, entity и timestamp  
- видны old/new values там, где это применимо

## US-014

**User Story:** Как viewer, я хочу просматривать админские данные без права редактирования, чтобы иметь доступ к информации без риска изменить её.  
**Acceptance Criteria:**  
- viewer может открыть разрешённые страницы  
- попытка выполнить изменяющий API-запрос возвращает `403`

## US-015

**User Story:** Как владелец бизнеса, я хочу получать новые заявки в Telegram, чтобы оперативно узнавать о входящих обращениях.  
**Acceptance Criteria:**  
- при успешной интеграции сообщение приходит в Telegram  
- при ошибке лид не теряется  
- результат фиксируется в `IntegrationLog`

## US-016

**User Story:** Как владелец бизнеса, я хочу видеть источник лида и UTM-метки, чтобы оценивать эффективность маркетинговых каналов.  
**Acceptance Criteria:**  
- source, utm-поля, landing page и referrer сохраняются  
- данные доступны в карточке лида и БД
