# Operator handoff

## Что такое operator handoff

`Operator handoff` — это сценарий, в котором пользователь в чат-виджете запрашивает подключение человека вместо продолжения обычной чат-воронки.

На текущем этапе это не live-chat и не real-time переписка. Мы просто фиксируем, что пользователь попросил оператора, и показываем такую чат-сессию в админке.

## Зачем нужен статус waiting_operator

Статус `waiting_operator` нужен, чтобы быстро находить сессии, где пользователь явно попросил человека.

Текущие статусы чат-сессий:

- `active`
- `waiting_operator`
- `operator_replied`
- `lead_created`
- `closed`

Если пользователь запросил оператора во время обычного сценария, сессия переходит из `active` в `waiting_operator`.

Если по этой сессии уже создан `Lead`, статус `lead_created` не затирается назад, но системное сообщение о запросе оператора всё равно сохраняется.

## Как пользователь запрашивает оператора

В `components/chat/ChatWidget.tsx` есть кнопка `Позвать оператора`.

При нажатии:

1. Вызывается API handoff
2. В Метрику отправляется цель `chat_operator_request`
3. Пользователь видит мягкое сообщение:
   что диалог передан оператору и что контакт поможет ответить быстрее

Это не ломает существующую воронку и не мешает дальнейшей отправке заявки через `/api/lead`.

## Какой API вызывается

Используется route:

`POST /api/chat/session/[id]/handoff`

Route:

- находит `ChatSession`
- если сессия есть и статус `active`, меняет статус на `waiting_operator`
- создаёт `Message`:
  - `sender = "system"`
  - `text = "Пользователь запросил оператора"`

## Как фиксируется system message

System message нужен, чтобы в истории чата было видно не только пользовательские и бот-сообщения, но и служебные действия.

В данном случае он показывает момент, когда пользователь запросил оператора.

Это важно для аудита сценария и будущей операторской логики.

## Как админ видит чат-сессии

Для handoff добавлен раздел:

- `/admin/chats`
- `/admin/chats/[id]`

В списке чатов администратор видит:

- дату создания
- статус
- выбранную ветку
- наличие связанного `Lead`
- последнее сообщение

В карточке чат-сессии видны:

- основные поля сессии
- связанная заявка
- полный список сообщений

Если статус `waiting_operator`, он выделяется отдельным бейджем.

## Почему пока без WebSocket

На этом этапе handoff сделан без WebSocket, потому что сейчас задача — зафиксировать намерение пользователя и дать администратору видимость таких диалогов.

Для этого достаточно:

- сохранить статус сессии
- создать system message
- показать список и карточку чат-сессий в админке

Так проект получает полезный операторский слой без усложнения инфраструктуры.
