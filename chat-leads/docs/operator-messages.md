# Operator messages

## Зачем нужны operator messages

`Operator messages` нужны, чтобы администратор мог отвечать в рамках чат-сессии и сохранять эти ответы в общей истории диалога.

На текущем этапе это ещё не live-chat и не доставка ответа посетителю в реальном времени. Но система уже получает операторский слой поверх сохранённых чат-сессий.

## Почему используется отдельный admin API

Сообщения оператора создаются только через отдельный admin API:

`POST /api/admin/chats/[id]/messages`

Это нужно, чтобы:

- требовать `admin_session`
- не смешивать операторские действия с публичным API виджета
- не позволять посетителю подделывать `sender = "operator"`

## Почему публичный API не должен принимать sender=operator

Публичный route для чат-сообщений предназначен только для:

- `bot`
- `visitor`
- `system`

Если бы он принимал `operator`, любой клиентский запрос мог бы записать в историю фальшивый ответ оператора. Поэтому операторские сообщения должны создаваться только на защищённой админской стороне.

## Как сообщение сохраняется в Message

Admin API:

1. Проверяет cookie `admin_session`
2. Валидирует `text`
3. Ищет `ChatSession`
4. Создаёт `Message`:
   - `chatSessionId`
   - `sender = "operator"`
   - `text`

После этого сообщение сразу видно в карточке чат-сессии в админке.

## Как меняется статус ChatSession

После ответа оператора используется статус:

- `operator_replied`

Логика такая:

- если сессия была `waiting_operator`, она становится `operator_replied`
- если сессия была `active`, её тоже можно перевести в `operator_replied`
- если сессия уже `lead_created` или `closed`, сообщение всё равно разрешено сохранить, но статус не меняется

## Ограничение текущего этапа

Сейчас операторский ответ только сохраняется в истории чата.

Пользовательский виджет пока:

- не получает его автоматически
- не использует polling
- не использует WebSocket

То есть это backend/admin-подготовка к следующему этапу real-time коммуникации.

## Что дальше

Следующий логичный шаг:

- polling или WebSocket для доставки операторских сообщений в виджет посетителя

После этого можно будет развивать:

- live-chat
- online/offline статусы
- typing indicators
- назначение оператора
- полноценный handoff в реальном времени
