# Non-Functional Requirements

## Безопасность

- Админка должна быть доступна только авторизованным пользователям по cookie `admin_session`.
- Роли `admin`, `operator`, `viewer` должны ограничивать доступ к операциям изменения данных.
- Пароли пользователей должны храниться только в виде hash.
- `passwordHash` не должен возвращаться на клиент.
- Секреты интеграций не должны попадать в клиентский код.

## Персональные данные

- Контактные данные лида должны храниться в PostgreSQL в пределах серверного контура.
- В аудит и журналы интеграций не должны попадать plain passwords.
- `IntegrationLog` не должен хранить секреты доступа к Telegram или CRM.

## Доступность

- Приложение должно работать по HTTPS.
- `PM2` должен обеспечивать автозапуск процессов после рестарта сервера.
- При недоступности WebSocket базовый сценарный чат и HTTP API должны оставаться работоспособными.

## Отказоустойчивость

- Ошибка внешней интеграции не должна приводить к потере лида.
- Сообщения real-time чата должны сохраняться в БД независимо от жизненного цикла клиентской страницы.
- При недоступности Telegram лид должен оставаться доступным в админке со статусом ошибки.

## Производительность

- Основные списки админки должны ограничиваться разумным объёмом выборки для MVP.
- Real-time обмен сообщениями должен происходить с задержкой, приемлемой для операторского диалога.
- Логика сценарного чата должна отрабатывать без обязательной зависимости от внешних сервисов.

## Логирование

- Ошибки интеграций должны фиксироваться в `IntegrationLog`.
- Ошибки runtime, не обрабатываемые доменной логикой, должны попадать в серверные логи процесса.

## Аудит

- Все ключевые действия администратора и оператора должны записываться в `AuditLog`.
- Аудит должен включать исполнителя, тип действия, сущность и временную метку.

## Резервное копирование

- PostgreSQL не должен быть открыт наружу без необходимости.
- Резервное копирование БД рекомендуется выполнять через `pg_dump` по `cron`.
- Бэкапы должны храниться вне каталога приложения и иметь политику ротации.

## Поддерживаемость

- Архитектура должна оставаться понятной для одного разработчика или маленькой команды.
- Документация по API, WebSocket, процессам и модели данных должна храниться рядом с проектом в `docs`.
- Изменения интеграций должны выполняться без полного переписывания доменной модели.

## Масштабируемость

- Модульный монолит должен допускать выделение integration layer в отдельный сервис на следующем этапе.
- Отдельный процесс `Socket.IO` должен позволять развивать real-time слой независимо от основного web-процесса.
- При росте нагрузки должны быть возможны вынесение очередей интеграций и масштабирование PostgreSQL.
