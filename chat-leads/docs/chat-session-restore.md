# Восстановление чат-сессии

## Зачем нужна persistence чат-сессии

Если пользователь обновляет страницу, локальный React state виджета сбрасывается. Без persistence это приводит к потере истории диалога в UI, даже если сама `ChatSession` и все `Message` уже сохранены в PostgreSQL.

Поэтому виджет хранит идентификатор сессии локально и при следующем открытии восстанавливает историю из backend.

## LocalStorage key

Используется ключ:

`chat_leads_chat_session_id`

Что происходит:

- при создании новой `ChatSession` её `id` сохраняется в `localStorage`
- при восстановлении страницы этот `id` читается обратно
- при `Начать сначала` ключ удаляется, а старая сессия в БД не трогается

## Как восстанавливается sessionId

При монтировании `ChatWidget`:

1. проверяется `localStorage`
2. если `chat_leads_chat_session_id` найден, вызывается backend route
3. если сессия существует, виджет восстанавливает:
   - `sessionId`
   - сообщения
   - статус
   - realtime-подключение
4. если сессия не найдена, ключ удаляется и виджет работает как новый

## Какой API используется для загрузки истории

Используется публичный route:

`GET /api/chat/session/[id]`

Он возвращает:

- `id`
- `status`
- `selectedOption`
- `summary`
- `leadId`
- даты сессии
- массив `messages`

Без лишних данных `Lead`.

## Как предотвращаются дубли сообщений

Дубли предотвращаются на двух уровнях:

1. при восстановлении история берётся из БД как источник истины
2. при `message:new` из Socket.IO сообщение добавляется только если его `id` ещё нет в локальном state

Это защищает от повторного `chat:join`, reconnect и повторной доставки одного и того же события.

## Как это связано с WebSocket

После восстановления `sessionId` виджет снова подключается к Socket.IO и делает:

`chat:join { sessionId, role: "visitor" }`

Благодаря этому:

- история уже есть в UI
- новые operator messages продолжают приходить realtime
- visitor может продолжать писать в чат, если сессия в состоянии handoff

## Поведение по статусам

- `active`:
  история восстанавливается, дальше пользователь может продолжить работу с виджетом
- `waiting_operator` / `operator_replied`:
  история восстанавливается, доступно поле для свободного сообщения оператору
- `lead_created`:
  история восстанавливается и показывается финальное состояние:
  `Заявка уже отправлена. Мы свяжемся с вами в течение дня.`

## Что будет дальше

Следующие логичные шаги:

- `visitorId` / `cookieId` для более устойчивой идентификации посетителя
- автозакрытие старых сессий по таймауту
- авторизация посетителя
- более точное восстановление шага сценарной воронки
