# Integration Logs

## Зачем нужны IntegrationLog

`IntegrationLog` нужен, чтобы фиксировать каждую попытку отправки заявки во внешние сервисы. Это позволяет видеть не только итоговый статус заявки, но и технический результат конкретной интеграции.

## Какие внешние сервисы логируются сейчас

Сейчас логируется отправка заявки в Telegram.

## Поля модели IntegrationLog

- `id` — идентификатор лога
- `leadId` — ссылка на заявку
- `lead` — связь с моделью `Lead`
- `service` — имя внешнего сервиса, например `telegram`
- `status` — технический статус попытки, например `success` или `failed`
- `requestPayload` — безопасный JSON запроса без секретов
- `responsePayload` — ответ внешнего сервиса, если он есть
- `errorMessage` — текст ошибки при неудаче
- `createdAt` — дата и время создания лога

## Связь Lead → IntegrationLog

У одной заявки может быть несколько интеграционных логов. Это важно, потому что заявка может отправляться в несколько систем или повторно отправляться в один и тот же сервис.

## Почему нельзя хранить токены в payload

Секреты вроде `TELEGRAM_BOT_TOKEN` нельзя сохранять в логах, потому что логи могут читать администраторы, разработчики или системы мониторинга. В логах должны оставаться только безопасные данные, необходимые для диагностики.

## Как это помогает диагностике интеграций

`IntegrationLog` помогает понять:

- что именно отправлялось во внешний сервис
- какой ответ вернулся
- на каком этапе произошла ошибка
- была ли проблема в данных, конфигурации или самом внешнем сервисе

## Как это будет расширяться дальше

Позже можно добавить:

- CRM-интеграции
- retry-механику
- `IntegrationJob`
- повторную отправку
- статусы `pending` / `processing` / `success` / `failed`
