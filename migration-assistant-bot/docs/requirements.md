# Требования — Migration Assistant Bot

## Функциональные требования

### Сценарный чат
- FR-001. Система должна показывать пользователю стартовый экран с основными сценариями взаимодействия.
- FR-002. Система должна вести пользователя по предопределённым сценариям в зависимости от выбранной ветки.
- FR-003. Система должна позволять пользователю возвращаться к следующему шагу сценария после получения ответа.
- FR-004. Система должна поддерживать разделение сценариев по бизнес-веткам: консультация, покупка шаблона, заказ услуги, оставление заявки.

### Онлайн-консультация
- FR-005. Система должна показывать список тем для онлайн-консультации.
- FR-006. Система должна выдавать пользователю ответ по выбранной теме.
- FR-007. Система должна предлагать следующий шаг после ответа в консультационном сценарии.

### Покупка шаблона
- FR-008. Система должна показывать список доступных цифровых продуктов и шаблонов документов.
- FR-009. Система должна показывать описание выбранного шаблона перед оплатой.
- FR-010. Система должна собирать контактные данные пользователя перед оплатой шаблона.
- FR-011. Система должна создавать платёж для выбранного шаблона.
- FR-012. Система должна выдавать PDF пользователю только после подтверждённой оплаты.

### Заказ услуги
- FR-013. Система должна позволять пользователю выбрать услугу.
- FR-014. Система должна собирать данные, необходимые для оформления заказа услуги.
- FR-015. Система должна принимать предоплату за услугу через платёжный сценарий.
- FR-016. Система должна создавать лид после успешной оплаты услуги.

### Оставление заявки
- FR-017. Система должна собирать ответы пользователя в анкете.
- FR-018. Система должна сохранять контактные данные пользователя в сценарии оставления заявки.
- FR-019. Система должна создавать лид после завершения сценария заявки.

### Оплата
- FR-020. Система должна создавать платёж через интеграцию с YooKassa.
- FR-021. Система должна получать `confirmation_url` и возвращать ссылку пользователю.
- FR-022. Система должна проверять текущий статус платежа по `payment_id`.
- FR-023. Система должна принимать webhook от YooKassa об изменении статуса платежа.
- FR-024. Система должна исключать повторную обработку одного и того же webhook или `payment_id`.

### CRM
- FR-025. Система должна создавать лид в Bitrix24 CRM после подтверждённой оплаты либо после завершения сценария заявки.
- FR-026. Система должна передавать в CRM имя, телефон, источник, сценарий и данные по продукту или услуге.

### Telegram
- FR-027. Система должна отправлять менеджеру уведомление после создания лида или подтверждённой покупки.
- FR-028. Система должна передавать в уведомление ключевые данные пользователя и сценария.

### Аналитика
- FR-029. Система должна фиксировать ключевые пользовательские события для аналитики поведения.
- FR-030. Система должна сохранять результат оплаты для последующей аналитики и контроля сценария.

## Нефункциональные требования
- NFR-001. Пользовательский сценарий должен быть понятным и линейным, без необходимости вручную разбираться в маршруте обработки.
- NFR-002. Система должна использовать JSON как формат обмена данными во внешних интеграциях.
- NFR-003. Система должна обеспечивать идемпотентность обработки webhook оплаты.
- NFR-004. Система не должна выдавать PDF до подтверждения успешной оплаты.
- NFR-005. Система должна сохранять данные пользователя даже при ошибке одной из интеграций.
- NFR-006. При недоступности CRM данные для лида не должны теряться.
- NFR-007. При недоступности Telegram уведомления ошибка не должна блокировать основной бизнес-сценарий.
- NFR-008. Система должна обеспечивать трассируемость сценария по событиям, заявке и оплате.
- NFR-009. Система не должна повторно создавать лид или покупку при дубле webhook.
- NFR-010. Система должна обеспечивать безопасную обработку персональных данных пользователя и явное согласие перед отправкой заявки.
